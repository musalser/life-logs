# ТЗ: Извлечение знаний из рукописей и дневника

> Версия: 1.0. Исполнитель: DeepSeek-V41-flash.
> Статус решений: все архитектурные выборы согласованы с заказчиком (см. раздел 3).

---

## 1. Контекст и цель

Проект «life-logs» оцифровывает семейный архив: рукописные дневники распознаются
(HTR, kraken), обычный дневник пишется вручную (вкладка «Дневник»). Нужно из
любого текста — и рукописного, и печатного — извлекать знания:

- сущности и факты (сейчас недоделано: `DiaryService.extract_entities` не вызывается, NER-задача Celery не ставится в очередь, факты нигде не сохраняются);
- цели, события, привычки, связи с людьми (работает только для DiaryPage, синхронно в HTTP-запросе, без дедупликации на эмбеддингах и без учёта перспективы автора).

Цель: единый конвейер извлечения знаний для **двух типов источников** (страница
рукописи и страница дневника), с дедупликацией, учётом перспективы автора,
аналитикой и RAG в чате. Медленные функции во время разработки выполняются
синхронно, но архитектура проектируется под асинхронное выполнение воркерами.

## 2. Термины

| Термин | Значение |
|---|---|
| **Источник (Source)** | Единица текста, из которой извлекаются знания: подтверждённая страница рукописи (`htr`) или страница дневника (`diary`) |
| **Объект (Entity)** | Сущность из базы знаний; в первую очередь — персона (`entity_type='person'`) |
| **«Я» (self-сущность)** | Объект-персона, привязанный к аккаунту авторизованного пользователя: одна сущность на каждого `User`, ссылка `users.self_entity_id` |
| **Автор текста** | Объект, от лица которого написан текст источника. Для рукописи — объект, привязанный к `HTRAuthor`; для дневника — self-сущность авторизованного пользователя |
| **Перспектива** | Отношения и факты извлекаются от лица автора текста, а не от лица пользователя |
| **Дедупликация** | Слияние повторных упоминаний одной сущности/цели/привычки/события в одну запись БД |
| **Переизвлечение** | Повторный запуск конвейера по источнику с заменой всех знаний, порождённых этим источником (идемпотентно) |

## 3. Согласованные архитектурные решения

1. **Модель LLM:** `qwen3:14b` — для извлечения знаний, чата, заголовков дневника.
   HTR-коррекцию строк оставить на `gemma3:12b` (не трогать).
2. **Эмбеддинги:** `google/embeddinggemma-2` (740m: текстовый бэкбон 270m плюс
   подгружаемые vision/audio-энкодеры), размерность 768. Загружается **в
   процессе** через `sentence-transformers`, а не через Ollama: эмбеддинг не
   встаёт в очередь за 14b-генерацией чата. Требуется
   `sentence-transformers>=6.1.0` и `transformers>=5.19` (архитектура
   `embedding_gemma2` в более старых версиях не распознаётся).
3. **Хранение векторов:** pgvector в Postgres. Образ в docker-compose меняется на
   `pgvector/pgvector:pg16` (существующий volume `postgres-data` сохраняется).
4. **Рукопись → дневник:** ничего не копируется. Вводится универсальный источник
   (п. 6); подтверждённая страница рукописи сама становится источником текста.
   Пайплайн общий для `htr` и `diary`.
5. **Переизвлечение:** автоматически при любом изменении текста источника
   (пере-подтверждение, reopen + правки, PUT дневника). Полная замена знаний по
   источнику, идемпотентно.
6. **Родственные связи:** храним только прямые рёбра от автора
   `(from → to, type)`. Производные отношения («прабабушка») не материализуем;
   в UI показываем **путь** по графу. Привязка автора к «известному объекту»
   обязательна и выбирается пользователем.
7. **«Я» как объект:** у каждого авторизованного пользователя (аккаунта) есть
   свой объект-персона — self-сущность, создаётся при регистрации
   (`users.self_entity_id`). Знания, извлечённые со вкладки «Дневник»,
   атрибутируются именно этому объекту (`subject_entity_id` = сущность юзера,
   под которым он вошёл). На вкладке «Знания» — селектор объекта, по умолчанию
   «Я».
8. **Аналитика:** блок внизу вкладки «Знания», генерация по кнопке с кэшем,
   инвалидация кэша при новых знаниях. Каждый инсайт/вопрос/идея/вывод ссылается
   на источники.
9. **RAG в чате:** тумблер (по умолчанию включён) + выбор объекта, по которому
   фильтруются чанки.
10. **Асинхронность:** конфиг `KNOWLEDGE_PROCESSING_MODE=sync|async` (по умолчанию
    `sync` для разработки). Оба режима вызывают один и тот же пайплайн.

   knowledge_processing_mode: str = "sync"  # sync | async

   knowledge_dedup_candidates: int = 5

   rag_enabled_by_default: bool = True
   rag_top_k: int = 4
   rag_chunk_max_chars: int = 1200
   rag_chunk_overlap_chars: int = 200

   knowledge_neighbor_context_chars: int = 400

4. **Адаптер Ollama:**
   - `MODEL` берётся из `settings.llm_model` (не хардкод).
   - Для всех структурированных вызовов: `options={"think": False,
     "temperature": 0.1}` + префикс `/no_think` в промпте (qwen3 умеет думать,
     иначе тратит бюджет и ломает JSON).
   - `generate_structured` — fallback: если ответ не парсится как JSON или пуст
     (`done_reason` не `stop`), повторить через `format="json"` + существующий
     `_extract_json`-подход (регэксп по фигурным скобкам).
   - Эмбеддинги в адаптере отсутствуют: они считаются в процессе
     (`EmbeddingService` + `sentence-transformers`), см. 4.5.

- Тесты: `tests/test_embedding_service.py`, `tests/test_ollama_adapter.py`.

Ограничения среды (важно для этапов 4 и 6):

- Ollama на хосте — 0.34.4, но эмбеддинги от него больше не зависят: модель
  качает `sentence-transformers` из Hugging Face. В `backend/.env` больше нет
  `EMBEDDING_MODEL`.
- **GPU сейчас недоступен** (`torch.cuda.is_available()` → False, NVML не
  инициализируется), поэтому `embedding_device="auto"` выбирает CPU. Замеры на
  CPU: загрузка весов из кэша ~17 с, кодирование 12 коротких строк ~5,5 с,
  одной строки — доли секунды. Для RAG-индексации это терпимо, но при появлении
  GPU достаточно выставить `EMBEDDING_DEVICE=cuda` (или оставить `auto`).
- **Промпт решает больше, чем кажется (важно для этапов 4 и 6).** Замеры на 20
  связанных и 20 несвязанных русских парах (полная мультимодальная модель, bf16,
  CPU). «Анизотропия» — средний косинус вектора к среднему вектору набора: чем
  ближе к 1, тем сильнее всё сжато в один узкий конус.

  | промпт | связанные | несвязанные | запас | AUC | анизотропия |
  |---|---|---|---|---|---|
  | `Clustering` (был выбран) | 0.983 | 0.922 | 0.061 | 0.950 | 0.956 |
  | `Classification` | 0.927 | 0.739 | 0.188 | 0.950 | 0.857 |
  | без префикса | 0.944 | 0.760 | 0.184 | 0.965 | 0.862 |
  | `Document` | 0.941 | 0.756 | 0.185 | 0.963 | 0.865 |
  | `SearchQuery` | 0.939 | 0.695 | **0.244** | 0.970 | **0.828** |
  | **`SentenceSimilarity`** | 0.961 | 0.814 | 0.147 | **0.983** | 0.900 |

  `Clustering` — худший вариант для дедупликации: минимальный запас и почти
  вырожденное пространство. Именно он давал «купить молоко ↔ похудеть к лету =
  0.920». По умолчанию выбран `SentenceSimilarity`: это ровно та симметричная
  задача, что нам нужна («measuring similarity» в карточке модели), у него лучший
  AUC, а фон ниже (0.814), поэтому top-k перестаёт забиваться случайными фразами.
  После смены промпта та же пара даёт **0.797**, «Баба Галя ↔ дед Иван» — 0.874,
  «Баба Галя ↔ бабушка Галя» — 0.968.

  Следствия:
  1. **Абсолютный порог не решает слияние.** Даже у лучшего промпта хвосты
     перекрываются (~2 % ошибок на лучшем пороге), а два *разных* дня рождения
     одного ребёнка дают 0.955. Поэтому эмбеддинг только **отбирает** top-k
     кандидатов (`knowledge_dedup_candidates`) с отсечкой
     `knowledge_dedup_min_similarity = 0.88` (чуть выше среднего фона 0.814),
     а решение принимает **LLM-resolver**.
  2. Поверх — детерминированные предохранители: у событий сравнивать даты из
     `time_text` (разные даты → никогда не сливать), у персон — алиасы
     (`entities.aliases_json`).
  3. Порог — это лишь «дорого ли звать LLM»; при сомнении лучше позвать, потому
     что неслиянный дубль остаётся в данных навсегда.

  Два проверенных побочных факта: **bfloat16 и float32 дают идентичные векторы**
  (AUC 0.970 у обоих), так что кастовать dtype не нужно (а `float16` карточка
  модели прямо запрещает — векторы деградируют молча); загрузка **только
  текстового энкодера** (`embedding_text_only`, vision/audio не нужны)
  укладывает модель в 271M параметров с теми же векторами — память процесса
  падает с ~1,5 ГБ до ~0,5 ГБ.

  Отдельно про RAG: `SearchQuery`↔`Document` даёт меньший запас, чем ожидалось
  («что пекла бабушка?» ↔ «бабушка испекла пирог с яблоками» = 0.784 против 0.723
  у нерелевантного документа). На этапе 6 ранжирование надо проверить на реальных
  вопросах; если запаса не хватит — считать запрос и чанки одним промптом или
  добавить реранкер.

Инфраструктурная находка: контейнеры были созданы из Windows-копии проекта и
держали данные в `C:\Users\Sasha\github.com\musalser\life-logs\backend\postgres-data`,
а рабочая копия в WSL смотрела в свой пустой каталог. Данные перенесены в
`backend/postgres-data` рабочей копии (оригинал на Windows не тронут), Redis
переведён на `backend/redis-data`. Если Windows-копия ещё нужна — решить, какая
из двух каноническая, чтобы базы не разъехались.

### 5.3 Миграция данных

1. `CREATE EXTENSION IF NOT EXISTS vector;`
2. Для каждого `User` создать self-сущность: `entity_type='person'`,
   `canonical_name = User.name`; установить `users.self_entity_id` на неё.
   В `POST /auth/register` self-сущность создаётся вместе с аккаунтом.
3. Существующие `EntityRelation` перенести в рёбра `from=self_entity →
   entity`, `relation_type` сохранить; `source_id` оставить NULL (исторические
   данные, переизвлечение по кнопке).
4. Для каждого существующего `DiaryPage` создать `knowledge_sources` запись
   (`source_type='diary'`, `text=content`, `extraction_status='pending'`) и
   перенаправить FK во всех дочерних таблицах.
5. Для каждого подтверждённого `HTRPage` создать `knowledge_sources`
   (`source_type='htr'`, собрать текст из строк, см. 6.1,
   `extraction_status='pending'`).
6. Для каждого `HTRAuthor` без `entity_id`: создать сущность-персону с именем
   автора и привязать (пользователь может перепривязать в UI).

## 6. Единый источник текста (SourceText)

### 6.1 Сборка текста рукописи

При подтверждении страницы `HTRPage`:

- текст строки = `corrected_text` (если есть) иначе `predicted_text`;
- `text = "\n".join(line_text for line in lines по order_index)`;
- `line_map[i] = {line_id, start, end}` — офсеты каждой строки в собранном
  тексте (учитывая `\n` между строками);
- `title = file_name или "Стр. #N"`.

Пересборка при каждом confirm/reopen. Если `text_hash` не изменился, а
подтверждение повторное — переизвлечение всё равно запускается (обновление
знаний обязательно, см. 6.3).

### 6.2 Контекст соседних страниц (обрыв предложения)

Предложение может начинаться в конце страницы N−1 и продолжаться на странице N.
При запуске конвейера для источника типа `htr` в LLM-промпты добавляется
контекстный блок:

- хвост предыдущей подтверждённой страницы того же автора (последние
  `knowledge_neighbor_context_chars` символов) и голова следующей (первые
  `knowledge_neighbor_context_chars` символов), страницы по `order_index`;
- контекст помечается явно: «Контекст (НЕ извлекай из него): ...»;
- извлекаются знания **только из текста текущей страницы**; атрибуция
  (offsets, source_id) — только текущая страница.

Для `diary` контекст не обязателен; допускается хвост предыдущей записи.

### 6.3 Жизненный цикл и статусы

```
[confirm/save] → источник создан/обновлён (text_hash) → extraction_status=pending
   → запуск конвейера (sync: в запросе; async: celery) → status=running
   → done | failed (error, extraction_runs запись)
```

- **confirm страницы рукописи:** собрать текст → upsert `knowledge_sources` →
  запустить конвейер.
- **reopen страницы рукописи:** пометить источник `pending`, **удалить** знания,
  порождённые этим источником (та же процедура, что в 7.4), UI скрывает
  подсветку. Повторное подтверждение переизвлечёт.
- **PUT /diary/pages:** upsert источника (новый hash) → переизвлечение.
- **DELETE /diary/pages:** удалить источник и его знания (каскад + очистка 7.4).
- Защита от дублей: если `extraction_status='running'`, повторный запуск не
  создаёт вторую задачу (redis-lock или проверка статуса).

## 7. Конвейер извлечения

Единая функция `run_extraction(source_id) -> dict` (модуль
`app/services/extraction_pipeline.py`). Вызывается либо напрямую (sync-режим),
либо из Celery-задачи `app.tasks.extract_knowledge(source_id)`.

### 7.1 Шаги

1. Загрузить source + соседний контекст (6.2).
2. LLM-вызовы (все — `think:false`, `format=schema`, fallback JSON; каждый вызов
   в своём try/except — сбой одного типа не роняет остальные):
   - **A. Entities + mentions + facts** (реанимировать и доработать
     `DiaryService.extract_entities`): сущности (`entity_ref`, тип, canonical,
     aliases, description), упоминания (`entity_ref`, точная подстрока,
     `start_offset/end_offset` 0-based эксклюзивно в тексте источника), факты
     (`subject_entity_ref` default = автор, `predicate`, `object_entity_ref` /
     `object_text`, `source_text` — точная цитата, offsets, `time_text`,
     `confidence`). Правило: `mention_text`/`source_text` обязаны быть
     подстроками текста; офсеты валидируются сервером (иначе — отбрасывать
     элемент).
   - **B. Relations:** связи **от автора текста**: `person_name`, `relation_type`
     (словарь: мама/папа/сестра/брат/бабушка/дедушка/жена/муж/сын/дочь/друг/
     подруга/коллега/начальник/сосед/знакомый...), `source_text`, offsets,
     `confidence`. Промпт явно получает «Автор этого текста: <имя объекта>» и
     инструкцию: «мама» = мама автора, а не читателя.
   - **C. Goals, D. Events, E. Habits:** как сейчас в `KnowledgeService`, но с
     обязательными `source_text` и offsets, и subject = автор.
3. **Дедупликация** (7.2).
4. **Запись** (7.3, 7.4) — одной транзакцией.
5. Инкремент `knowledge_state.version` (инвалидация аналитики), запись в
   `extraction_runs`, `extraction_status='done'`.

### 7.2 Дедупликация эмбеддингами + LLM

Эмбеддинг-текст (нормализованный, lower + strip):

- сущность: `canonical_name` + aliases;
- цель: `title` (+ описание);
- привычка: `title`;
- событие: `title` + `time_text` + описание (time_text обязателен, иначе
  «день рождения 2023» сольётся с «день рождения 2024»).

Алгоритм (для кандидата):

1. `embed_texts(..., prompt_name="SentenceSimilarity")` (симметричная близость,
   см. 4.5) → поиск top-`knowledge_dedup_candidates` существующих записей того же
   пользователя и типа (pgvector cosine distance, фильтр `subject_entity_id`).
2. Если лучший кандидат ниже `knowledge_dedup_min_similarity` (0.88) →
   **создать новую запись**, LLM не беспокоить.
3. Иначе отдать top-k кандидатов в LLM-resolver (`RESOLUTION_SCHEMA`,
   «сопоставляй только при уверенном совпадении») → merge или create.
   Автоматического слияния по одному косинусу **нет**: замеры (4.5) показывают
   ~0.92 у несвязанных фраз и 0.995 у двух разных дней рождения.
4. Предохранители до и после LLM:
   - **события:** если у кандидата и у нового события есть `time_text` с
     разными датами — слияние запрещено, что бы ни сказала модель;
   - **персоны:** при слиянии пополнить `aliases_json` новым написанием имени;
   - **цели/привычки:** merge только при явном совпадении смысла (тот же
     результат, разные формулировки), смена статуса — через `GoalProgress`.
5. **Факты не дедуплицируются эмбеддингами.** Правило: если существует факт с
   тем же `(subject_entity_id, predicate, object_entity_id/object_text)` — не
   создавать дубль, обновить `confidence`/`source_text`/offsets, если новый
   увереннее/полнее.

Настройки — в конфиге (раздел 4). Эмбеддинги записей без вектора (мигрированные)
досчитываются лениво при первом участии в поиске.

### 7.3 Атрибуция и перспектива

- У всего извлечённого (`facts`, `mentions`, `relations`, `goals`, `events`,
  `habits`) обязателен `source_id` и offsets в тексте источника.
- `subject_entity_id` = `author_entity_id` источника, если модель явно не
  указала другой субъект (для фактов-целей/событий/привычек).
- Для `diary`-источников `author_entity_id` = self-сущность **авторизованного
  пользователя** (`users.self_entity_id`): знания из дневника атрибутируются
  объекту того юзера, под которым он вошёл на сайт.
- Для `htr`-источников — объект, привязанный к `HTRAuthor.entity_id`; если
  привязки нет (NULL) — конвейер не запускается, статус `failed` с понятной
  ошибкой «привяжите автора к объекту», UI показывает диалог привязки.

### 7.4 Идемпотентное переизвлечение

В одной транзакции:

1. Удалить по `source_id`: `entity_mentions`, `facts`, `goal_progress`,
   `events`, `habit_logs`, `entity_relations` (где `source_id` = текущий),
   `chunks`.
2. Удалить осиротевшие «головы», созданные этим источником: `Goal` (где
   `created_from_source_id = source.id` и нет других `goal_progress`),
   `Habit` (нет других `habit_logs`), `Entity` (нет упоминаний/рёбер/фактов и
   `first_seen` на этом источнике), `EntityRelation`-рёбра (входят в п.1).
3. Вставить заново всё извлечённое.

Результат: повторный прогон того же источника даёт идентичное состояние БД
(нет дублей).

### 7.5 Синхронный и асинхронный режим

- `KNOWLEDGE_PROCESSING_MODE=sync`: `run_extraction(source_id)` вызывается
  прямо из роута (await), ответ включает `extraction_runs` результат.
- `async`: роут ставит `extract_knowledge.delay(source_id)` и возвращает
  `202 + {status: "pending"}`; фронтенд опрашивает статус (8.1).
- Celery-задача использует синхронные вызовы: LLM — `ollama.Client` (или
  `asyncio.run` вокруг адаптера), эмбеддинги — `EmbeddingService.embed_texts_sync`;
  воркер-процесс держит синглтоны (адаптер, embedding-сервис) — по образцу
  `_get_ner()` в `tasks.py`. Помнить: загруженная embedding-модель занимает
  ~0,5 ГБ на процесс (текстовый энкодер), поэтому API и воркер держат по копии.

## 8. API

### 8.1 Знания

| Метод/путь | Описание |
|---|---|
| `GET /knowledge?subject_entity_id=N` | Все знания от перспективы объекта N (default — self): goals, relations (рёбра `from=N` + путь до self), events, habits, facts, entities-персоны, stats |
| `GET /knowledge/objects` | Список объектов для селектора: self первым, затем персоны по `last_seen_at desc` |
| `POST /knowledge/objects` | Создать объект (`name`, `aliases[]`) |
| `PATCH /knowledge/objects/{id}` | Переименовать / изменить aliases |
| `GET /knowledge/sources/{source_type}/{ref_id}/status` | `{status, last_extracted_at, error, last_run_stats}` |
| `POST /knowledge/sources/{source_type}/{ref_id}/extract` | Ручной перезапуск конвейера |
| `GET /knowledge/analytics?subject_entity_id=N` | Инсайты/вопросы/идеи/выводы: из кэша, если `version` совпадает, иначе `null + stale=true` |
| `POST /knowledge/analytics/refresh` `{subject_entity_id}` | Перегенерация (LLM) и сохранение кэша |

### 8.2 Привязка автора

| Метод/путь | Описание |
|---|---|
| `PUT /htr/authors/{author_id}/entity` `{entity_id}` | Привязать автора рукописи к известному объекту (или создать новый через `POST /knowledge/objects` и привязать) |
| `GET /htr/authors/{author_id}` | Добавить в ответ `entity_id`, `entity_name` |

### 8.3 Жизненный цикл источников

- `POST /htr/pages/{id}/confirm` — после подтверждения: upsert
  `knowledge_sources` (6.1) + запуск конвейера (sync/async).
- `POST /htr/pages/{id}/reopen` — сброс источника: `pending` + удаление знаний
  источника (7.4).
- `POST /diary/pages`, `PUT /diary/pages/{id}` — upsert источника + запуск.
- `DELETE /diary/pages/{id}` — удалить источник + знания.
- `GET /htr/pages/{id}/knowledge` — знания, привязанные к странице рукописи
  (факты/упоминания/события с offsets и line_id, вычисленным по `line_map`) —
  для подсветки в UI.

### 8.4 Чат (RAG)

- `POST /chat/` — новые поля запроса: `rag: bool = true`,
  `subject_entity_id: int | null`. Если `rag`:
  1. `embed_text(query, prompt_name="SearchQuery")` → top-`rag_top_k` чанков
     (pgvector), фильтр `user_id` и — при указании объекта — чанков источников
     этого объекта (`author_entity_id`), плюс всегда чанки self. Чанки
     индексируются асимметричным промптом `Document`;
  2. чанки подставляются в системный промпт с требованием «отвечай по
     контексту, цитируй источники; если ответа нет — скажи прямо»;
  3. использованные чанки сохраняются в `entries.context_json`.
- `GET /chat/history` — возвращать `context_json` (для показа цитат под
  старыми ответами).
- Стрим-ответ не меняется; фронтенд после завершения стрима запрашивает
  `GET /chat/history?limit=1` для получения цитат последнего ответа.

## 10. Аналитика

`AnalyticsService.generate(user_id, subject_entity_id)`:

- Вход (по перспективе объекта): факты, цели + прогресс, события, привычки +
  логи, рёбра, сущности. Агрегат ограничен сверху (например, последние 500
  фактов) — с защитой от переполнения контекста.
- LLM: qwen3:14b, `think:false`, structured schema, 4 списка:
  - `insights` — нетривиальные паттерны (напр., «все упоминания бега — по
    утрам после конфликтов»);
  - `questions` — осмысленные вопросы, на которые в данных пока нет ответа
    («кем работала мама Бабы Гали?»);
  - `ideas` — конструктивные следствия для пользователя;
  - `conclusions` — короткие обобщения по темам.
- Обязательно: каждый элемент — `evidence: [{kind: fact|goal|event|habit|
  relation|entity, id, label}]`; сервер валидирует, что ссылки существуют.
- Кэш: `knowledge_insights` с `version = knowledge_state.version`; при
  несовпадении `GET` возвращает `stale=true`, кнопка «Обновить» вызывает
  `refresh`.
- Промпт жёстко требует: «не выдумывай; если данных мало — верни пустые
  списки; каждый пункт — с ссылками».

## 11. Фронтенд

### 11.1 Вкладка «Рукописи» (`manuscripts.vue`)

1. **Подтверждение страницы:** после `confirmPage()` — опрос
   `GET /knowledge/sources/htr/{page_id}/status` (polling 1–2 с, до `done`/
   `failed`): бейдж у страницы «извлечение… / знания готовы / ошибка (+ кнопка
   «Повторить» → `POST .../extract`)».
2. **Привязка автора:** если у `HTRAuthor` нет `entity_id` — перед/после
   подтверждения модальное окно «Кто автор этой рукописи?»: выбрать из
   `GET /knowledge/objects` или создать новый объект → `PUT /htr/authors/{id}/
   entity`. Без привязки конвейер не запускается.
3. **Подсветка знаний:** переключатель «Показать знания». Строки, в которых
   есть факты/упоминания (по `line_map` + offsets), подсвечиваются; клик по
   строке открывает панель со списком знаний (факт, цитата, уверенность).
   После `reopen` подсветка скрывается.
4. Клик по карточке знания в панели — прокрутка к нужной строке.

### 11.2 Вкладка «Знания» (`knowledge.vue`)

1. **Селектор объекта** в шапке (self первым; хранить выбор в localStorage).
   Все секции фильтруются по `subject_entity_id`.
2. Секции: Цели / Круг общения (с путём по графу: «мама Бабы Гали») / События /
   Привычки / **Факты** / **Персоны и сущности**.
3. Каждая карточка: цитата-источник кликабельна → переход на страницу рукописи
   (`/manuscripts?page={id}&highlight={line_id}`) или дневника
   (`/diary?page={id}`), с подсветкой/скроллом к офсету.
4. **Блок «Аналитика» внизу:** кнопка «Сгенерировать/Обновить», списки
   инсайтов/вопросов/идей/выводов; каждый пункт раскрывает evidence-ссылки
   (кликабельны). Если кэш устарел — бейдж «данные изменились».

### 11.3 Чат (`chat.vue`)

- Тумблер «Искать по архиву (RAG)» — по умолчанию вкл; селектор объекта
  (default self).
- Под ответом — блок «Источники»: использованные чанки (текст-выдержка +
  название источника, кликабельны).
- Для стрима: после завершения запросить последний entry и показать источники.

### 11.4 Дневник (`diary.vue`)

- После сохранения — индикатор статуса извлечения (тот же polling по
  `GET /knowledge/sources/diary/{id}/status`).

## 12. Порядок реализации (этапы для разработчика)

1. **Инфраструктура (выполнено):** pgvector-образ, `google/embeddinggemma-2`
   через `sentence-transformers` (не Ollama), конфиги, qwen3:14b в адаптере
   (+ `think:false`, fallback JSON), `EmbeddingService`, Alembic-настройка.
2. **Схема БД и миграция (выполнено):** новые таблицы, изменения, перенос
   данных, backfill-скрипт (см. 5.4).
3. **Источник текста (выполнено):** `KnowledgeSourceService` (сборка строк +
   `line_map`, соседний контекст, статусы, sync/async запуск, Celery-задача,
   переизвлечение по 7.4 — см. 7.6).
4. **Конвейер:** вызовы A–E, дедупликация (эмбеддинги + LLM-resolver),
   идемпотентная запись, `extraction_runs`, инкремент версии.
5. **API:** эндпоинты 8.1–8.3, граф-пути, аналитика (10), привязка авторов.
6. **Фронтенд:** 11.1 → 11.2 → 11.4 → 11.3 (в таком порядке).
7. **Тесты и полировка** (13).

На каждом этапе — коммит с работающими тестами.

## 13. Тестирование

- **Юнит:** сборка текста страницы и `line_map` (в т.ч. пустые строки,
  последняя строка без `\n`); валидация offsets; дедупликация (пороги,
  merge/create, дубль факта); BFS-пути; инвалидация кэша аналитики.
- **Интеграция (фикстуры, ollama-fake):** полный прогон конвейера на
  фиктивной странице; **идемпотентность** (двойной прогон → одинаковое число
  строк); переизвлечение при изменении текста (старые знания исчезают);
  перспектива (связь «мама» атрибутируется автору, не self); обрыв предложения
  (факт, разорванный между страницами, извлекается на второй странице с
  контекстом первой); sync и async режимы дают одинаковый результат.
- **E2E (ручной чек-лист):** подтверждение страницы → знания появляются,
  подсветка работает, цитаты открывают страницу; выбор объекта в «Знаниях»
  меняет содержимое; RAG в чате отвечает по архиву и показывает источники,
  тумблер выключает; аналитика генерируется, ссылки валидны.

## 14. Критерии приёмки

1. Модель знаний/чата/заголовков — `qwen3:14b`; HTR-коррекция осталась на
   `gemma3:12b`; все структурированные вызовы работают без thinking.
2. «Подтвердить страницу» запускает извлечение; бейдж статуса, ошибки
   показываются и можно повторить; без привязки автора — понятный диалог.
3. У фактов/упоминаний/событий/целей/привычек есть ссылки на реальный текст
   (source + offsets), клик открывает страницу с подсветкой.
4. Предложение, оборванное на границе страниц, извлекается корректно за счёт
   контекста соседней страницы.
5. Связи строятся от автора текста: «мама» в дневнике Бабы Гали — ребро
   БабаГаля→мама; на вкладке от «Я» виден путь до неё; ничего не выдумывается
   и не пересчитывается в «прабабушку».
6. «Я» — обычный объект; селектор на вкладке «Знания» работает, self по
   умолчанию.
7. Дедупликация: одна и та же цель на двух страницах = один `Goal` с двумя
   прогрессами; персоны с разными написаниями сливаются (aliases).
8. Переизвлечение идемпотентно и происходит автоматически при изменении текста
   (reopen/правки/PUT).
9. RAG в чате: тумблер (вкл по умолчанию), источники-цитаты под ответом,
   фильтр по объекту.
10. Аналитика: кнопка, кэш, инвалидация, evidence-ссылки валидны.
11. `KNOWLEDGE_PROCESSING_MODE=sync` и `async` дают одинаковый результат;
    в async режиме UI не блокируется и опрашивает статус.
12. Существующие данные смигрированы, backfill переизвлекает их без потерь.

## 15. Вне скоупа (сознательно)

- Ручной UI для слияния объектов (merge) — только автоматический.
- Композиция родственных отношений («прабабушка» и т.п.).
- Многопользовательская конкурентность (одна семья = один пользователь).
- Отдельная векторная БД, реранкинг, гибридный поиск.
- Оценка качества промптов на реальных страницах — выполняется вручную после
  внедрения (по логам `extraction_runs`).
