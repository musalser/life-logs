# Кинематографические переходы между вкладками

Переход между «Чат / Дневник / Знания / Рукописи» — это не подмена одной стены
текста на другую, а смена фокуса: страница уходит в мягкое размытие и темноту,
в середине стоит один объект назначения, маршрут меняется **под этим размытием**,
и новая страница возвращается в фокус. Текста в переходе нет.

![Размытие и объект «Рукописи»](screenshots/cinematic-blur-manuscripts.png)

Обратный ход — размытие уходит, новая страница проявляется:

![Новая страница возвращается в фокус](screenshots/cinematic-blur-dissolve.png)

---

## 0. Как выключить

Один флаг в `frontend/app.config.ts` — и он сейчас **выключен**:

```ts
export default defineAppConfig({
  cinematicTransitions: false   // true — переходы включены
})
```

Выключено — значит выключено целиком, а не «спрятано за прозрачностью»: слой не
монтируется, сторож в роутере не регистрируется, слушатель Escape не вешается, а
1.5 МБ объектов раздела не предзагружаются в простое. Замерено на выключенном
флаге: клик по вкладке → смена маршрута за **112–154 мс**, запросов картинок из
`/landing/` — ноль, элементов `.cine` в DOM — ноль, ошибок в консоли — ноль.

Флаг читается из `app.config`, поэтому в dev переключается правкой строки без
перезапуска сервера. Если нужен переключатель, доступный ops-ам без пересборки,
сюда же можно добавить `runtimeConfig.public.cinematicTransitions` из переменной
окружения — в `plugins/cinematic.client.ts` читается одна строка.

## 1. Из чего это собрано

| файл | роль |
| --- | --- |
| `frontend/app.config.ts` | единственный переключатель переходов |
| `frontend/composables/useCinematicTransition.js` | таблица сцен (какой объект у какой вкладки), предзагрузка, рукопожатие с роутером |
| `frontend/components/CinematicCurtain.vue` | размытие, объект, GSAP-таймлайны |
| `frontend/plugins/cinematic.client.ts` | сторож `router.beforeEach` + хук `page:finish` |
| `frontend/components/TabNavLink.vue` | вкладка с глифом и прогрев картинки при наведении |
| `frontend/app.vue` | монтирует слой **вне** лейаутов |
| `scripts/cut_out_black_background.py` | вырезание фона у фотографий, снятых на чёрном |
| `frontend/public/landing/*.png` | объекты: бюст, фигура, рука, кузнец |

Слой живёт в `app.vue`, а не в `layouts/default.vue`, по двум причинам: переход
начинается ещё на лендинге (кнопка «Enter the Temple»), и лейаут меняется ровно
в середине перехода — узел, который его прячет, не должен меняться вместе с ним.

## 2. Почему переход стадится в роутере, а не в ссылке

Соблазнительно повесить `@click.prevent` на каждую вкладку. Тогда переход
работает только там, где мы не забыли переписать ссылку, и расходится с кнопкой
«назад». Поэтому переход стадится в единственном месте, через которое проходят
все попадания в раздел:

```
клик по вкладке
   │
   ├─ router.beforeEach ──► stageTransition(path)
   │                          сцена найдена? есть драйвер? не reduce?
   │                          → размытие нарастает, guard ЖДЁТ (0.55 с)
   │
   ├─ маршрут меняется — экран уже размыт и закрыт вуалью
   │
   ├─ Nuxt: page:finish — новая страница отрисована
   │      └─► finishTransition() → размытие уходит (0.6 с)
   │
   └─ router.onError / сторож на 5 с → снять вуаль в любом случае
```

Две детали, которые легко упустить:

* **`page:finish`, а не `await router.push`.** Промис навигации резолвится, когда
  маршрут подтверждён, — но страница в этот момент ещё может быть пустой
  (`onMounted`-загрузка данных). `page:finish` Nuxt вызывает после того, как
  компонент страницы отрисован, поэтому размытие снимается уже над готовым экраном.
* **Сторож на 5 секунд.** Если страница не резолвится (ошибка, вечная загрузка),
  читатель не остаётся перед размытым экраном.

Если слоя нет (SSR, выключенный флаг, отключённый компонент,
`prefers-reduced-motion`), оба входа — `stageTransition` и `finishTransition` —
ничего не делают, и роутер работает как раньше.

## 3. Что именно происходит на экране

Тайминги собраны в одной константе `CUT` в `CinematicCurtain.vue`:

```js
const CUT = {
  blurIn: 0.5,   // страница уходит в размытие и темноту
  settle: 0.55,  // вуаль непрозрачна — можно менять маршрут
  out: 0.6,      // новая страница возвращается в фокус
  pushIn: 0.85   // наезд камеры на объект, идёт через обе половины
}
```

Слоёв три: вуаль (тёмный градиент + `backdrop-filter`), тёплое гало и сам объект
по центру. Замеренный профиль (Chromium 1440×900, 61 fps в покое):

```
+  85 мс  вуаль 0.09, объект 0.00, масштаб 1.090
+ 378 мс  вуаль 0.75
+ 686 мс  вуаль 1.00 — экран закрыт
+ 846 мс  маршрут сменился (page:finish), начался обратный ход
+1424 мс  слоя больше нет в DOM
```

Объект всё время стоит на центральной линии (замер: максимальное отклонение
центра от центра экрана — 0.008 px) и за переход плавно наезжает
(`scale 1.09 → 1.00`, затем до 1.07 на уходе).

## 4. Как добавить или заменить сцену

Всё в одном месте — `TAB_SCENES` в `useCinematicTransition.js`:

```js
manuscripts: {
  path: '/manuscripts',
  plate: '/landing/forge-statue.png',  // вырезанный объект (PNG с альфой)
  fit: 'figure'                        // 'figure' — объект по центру, 'cover' — фон на весь экран
}
```

* `path` без сцены (например, `/list`) даёт обычную навигацию без размытия.
* Смена только query (другая страница дневника, другой автор рукописей) склейкой
  не считается: `to.path === from.path` → guard пропускает навигацию сразу.
* Объект должен быть **PNG с альфой**. Фотография с фоном в центре экрана будет
  выглядеть прямоугольником поверх размытия — см. следующий раздел.

## 5. Вырезание фона

У всех объектов, кроме кузнеца, альфа уже была. Для него написан
`scripts/cut_out_black_background.py` (rembg в этой среде не установлен, а фон
здесь известен — чистый чёрный):

```bash
python scripts/cut_out_black_background.py frontend/public/landing/forge-statue.png
```

![До и после вырезания фона](screenshots/cinematic-cutout-before-after.png)

Главное в этом скрипте — не порог яркости, а **связность**. Наивный порог
(«пиксель темнее N → прозрачный») превращает тёмную статую в призрак: её
собственные тени уходят в прозрачность. Поэтому фон определяется как тёмная
область, **соединённая с рамкой кадра**: тёмная складка внутри мрамора — не фон,
а чёрный просвет между рукой и головой — фон. Плюс un-premultiply по измеренному
фону, который убирает тёмную кайму по краям.

Если фон не чёрный (градиент, студия, улица) — нужен rembg, как в
`scripts/process_landing_images.py`, либо вырезание на стороне сервиса, который
генерирует картинку.

## 6. Объём: вращение объекта на несколько градусов

Объём нельзя получить из плоской фотографии в браузере: `rotateY` на 3–4°
математически сужает картинку на `cos(4°) = 0.998`, то есть не видно вообще, а на
больших углах объект читается как картонка. Нужен кадр, снятый/сгенерированный с
другой точки, — то есть внешний сервис. Ниже два рабочих маршрута; результат
обоих — последовательность кадров, которую движок уже умеет проигрывать.

### 6.1. Higgsfield — image-to-video с движением камеры

Сервис генерирует короткий клип из одной картинки и умеет управлять камерой
(орбита, панорама, зум) — это ровно то, что нужно.

1. **Подготовьте вход.** Лучше всего — уже вырезанный объект на **сплошном чёрном**
   фоне (тот же `forge-statue.png` после скрипта положить на чёрный холст), а не
   фотография с окружением: модели труднее «дорисовать» фон, чем не трогать его.
2. Загрузите картинку в режим **Image to Video**.
3. Промпт — только про движение, без переописания объекта:
   > Slow cinematic camera orbit around the marble statue, camera rotates about
   > 8 degrees to the right, the statue itself stays perfectly still, identical
   > lighting, identical pure black background, no morphing, no added details,
   > no text, 24 fps
4. Если в интерфейсе есть пресеты камеры (orbit / rotate / pan / zoom) — выберите
   орбиту с **минимальной** силой. «Crash zoom» и «dolly» меняют кадрирование и
   ломают совпадение с `plate`.
5. Длительность 3–5 с, разрешение 1080p, пропорции как у исходника.
6. Сгенерируйте 2–4 варианта и смотрите на **руки, молот и лицо** — они «плывут»
   первыми. Морфинг в кадре убивает весь эффект.
7. Скачайте MP4.

### 6.2. Nano Banana — те же ракурсы поштучно

Nano Banana (Gemini image editing) — не видео, а редактирование изображения.
Он даёт **отдельные ракурсы**, из которых можно собрать вращение:

> Same statue, same lighting, same camera distance and framing, pure black
> background. Rotate the camera about 6 degrees to the left around the statue.
> Keep every detail identical: the hammer, the fingers, the marble veins, the
> pose. Photorealistic, no text, no extra objects.

Сгенерируйте 3–4 угла (4°, 8°, 12°). Дальше два способа применения:

* **как ключевые кадры для Higgsfield** (start frame → end frame): сервис
  интерполирует между ними, и дрожание между отдельными генерациями исчезает —
  это лучший вариант;
* **как есть**: два-три ракурса, между которыми переходит плита (медленный
  кросс-фейд). Дешевле, но заметно, что это не вращение, а подмена.

Тот же сервис годится и для вырезания фона (промпт «remove the background
completely, keep only the statue, transparent PNG»), если нужного ракурса нет в
готовом виде.

### 6.3. Клип → кадры → переход

```bash
# 1. Кадры: обрезать начало/конец, отбросить лишнее, ужать в webp
mkdir -p frontend/public/landing/manuscripts
ffmpeg -i clip.mp4 -ss 0.2 -t 3.6 \
  -vf "fps=24,scale=760:-2" \
  -c:v libwebp -quality 74 \
  frontend/public/landing/manuscripts/frame-%03d.webp

# 2. Сколько получилось (число идёт в сцену)
ls frontend/public/landing/manuscripts | wc -l

# 3. Если фон в клипе не чёрный — вырезать его в webm с альфой
ffmpeg -i clip.mp4 \
  -vf "fps=24,scale=760:-2,colorkey=0x000000:0.12:0.06,format=yuva420p" \
  -c:v libvpx-vp9 -pix_fmt yuva420p frontend/public/landing/manuscripts/plate.webm
```

```js
// 4. В сцене — покадровая последовательность или видео:
manuscripts: {
  path: '/manuscripts',
  plate: '/landing/forge-statue.png',                                  // кадр-страховка
  frames: { pattern: '/landing/manuscripts/frame-%03d.webp', count: 96 }
  // video: '/landing/manuscripts/plate.webm'
}
```

Правила, которые экономят время:

* **первый кадр = `plate`**: пока кадры грузятся, виден статичный объект, и
  подмена не заметна;
* **последний кадр ≈ первый**, иначе при повторном переходе будет рывок;
* движок ждёт кадры **не дольше 0.9 с** и рисует те, что успели прийти; 60–120
  кадров при 24–30 fps — это 2–4 секунды клипа;
* бюджет: 96 кадров по 760 px в webp ≈ 60–90 КБ каждый, то есть 6–9 МБ на сцену.
  Если это много — 60 кадров и 640 px дают 2–3 МБ.

Проверено на этом проекте: с последовательностью из 48 кадров `<canvas>`
действительно рисуется и прокручивается (23 различных состояния картинки за один
переход), статичный `plate` виден под ним до прихода кадров.

## 7. Производительность: что измерено

Headless-браузер без GPU — пессимистичный конец диапазона, но сравнение вариантов
честное (кадров за 2 секунды перехода, в покое 61 fps):

| вариант | fps |
| --- | --- |
| как есть (`backdrop-filter: blur(22px)`) | 20–24 |
| **без `backdrop-filter` вообще** | **62** |
| `blur(10px)` вместо 22 | 28 |
| `blur(22px) saturate(0.7)` | 20 |
| без гало под объектом | 20 |

Выводы, которые стоили замеров:

* **размытие фона — самая дорогая часть всего перехода.** Это осознанный выбор:
  именно оно делает склейку, а не чёрный экран. На GPU-композитинге это один
  кэшированный слой, а не перерисовка каждый кадр; если на слабой машине всё же
  тяжело — удалите две строки `backdrop-filter` в `.cine__veil`, останется
  плавное затемнение;
* `saturate()` рядом с blur стоит ещё ~4 fps и визуально не даёт ничего — убран;
* у объекта **не должно быть** `drop-shadow` или иных нецветовых фильтров: замер
  на прошлой версии перехода — 7 fps против 41 при `brightness + contrast`.
  Гало под объектом — статичный радиальный градиент, а не тень;
* в `.cine` **нельзя** добавлять `contain: paint`, `filter`, `opacity` или
  `isolation`: элемент станет backdrop root, и вуаль будет размывать пустой бокс
  вместо страницы. Это записано и в CSS, и в комментарии к разметке.

## 8. Доступность и краевые случаи

* `prefers-reduced-motion: reduce` — слой не монтируется вовсе, навигация
  обычная (проверено).
* Флаг `cinematicTransitions: false` в `app.config.ts` — то же самое, но по
  решению владельца приложения, а не по настройке системы (раздел 0).
* Escape во время перехода проматывает текущую половину таймлайна; сам переход
  страницы не пропускается — иначе можно остаться на размытом экране без объекта.
* Ссылки остались ссылками: без JS, со средней кнопкой мыши и «открыть в новой
  вкладке» работает как раньше.
* Слой декоративен: `aria-hidden`, из дерева доступности не вынимает ничего.
* Кнопка «назад»/«вперёд» проходит через тот же guard и тоже стадится (проверено).
* Текста в переходе нет, поэтому лендинговые шрифты (Cinzel / Cormorant) на
  страницах приложения больше не грузятся — раньше их тянул именно переход.

## 9. Как это проверялось

Скриншоты и метрики снимались headless-Chromium'ом по рецепту из
`docs/browser-for-agents.md`, скриптами в `/tmp/pw`:

* `cine.mjs` — четыре прогона: вуаль непрозрачна **до** смены маршрута, объект на
  центральной линии, снятие вуали после отрисовки страницы, `prefers-reduced-motion`,
  клик по активной вкладке и «назад», лендинг → `/chat` через смену лейаута;
* `cine-off.mjs` — выключенный флаг: время клика, отсутствие слоя, отсутствие
  предзагрузки картинок;
* `cine-trace.mjs` — покадровая трасса прозрачности вуали, прозрачности, масштаба
  и геометрии объекта;
* `cine-perf.mjs` — A/B эффектов из таблицы выше;
* `cine-frames.mjs` — путь с покадровой последовательностью.

Проверяются инварианты, а не симптомы: «маршрут меняется не раньше, чем вуаль
стала непрозрачной», «центр объекта не уезжает от центра экрана больше чем на
пиксель», «после перехода в DOM не осталось слоя».

## 10. Чего пока нет

* Ни у одной сцены нет последовательности кадров: путь написан и проверен, но
  ждёт клипов из Higgsfield / Nano Banana (раздел 6).
* Переход на ту же вкладку не стадится — иначе клик по активной ссылке закрывал
  бы экран без причины.
* `rotateY`-объём из плоской картинки сознательно не делается: см. начало
  раздела 6.
