# Распознавание рукописного текста (HTR): текущие технические решения и метрики

Документ описывает систему «как есть» на текущий момент: инференс (включая
beam-декодирование с языковой моделью), сегментацию, обучение персональной модели,
словарную проверку и правки языковой моделью. Предназначен для внешнего анализа:
где искать улучшения.

Дата срезa: корпус 8 подтверждённых страниц, активная модель v12.

без ML-бэкенда (распознавание тогда отвечает 422 с внятным текстом).

## 2. Распознавание (инференс)

**Модель.** Базовая — `ppocrv6_medium.safetensors` (PP-OCRv6 medium, 61 МиБ, ~15.9 млн
параметров, 1622 класса кодека). Загружается через kraken `load_safetensors(tasks=["recognition"])`.

**Сегментация.** По умолчанию нейросетевая — встроенная в kraken модель **bLLA**
(`SegmentationTaskModel`), даёт *полигоны*, следующие за изогнутой строкой, а не
прямоугольники. Есть резервный классический сегментер (`kraken.pageseg`, проекционный
профиль), включается настройкой `htr_segmentation_engine="classical"` или автоматически,
если нейросетевую не удалось загрузить (нужен `coremltools` для весов bLLA).

**Склейка разорванных строк** (`htr_segmentation_merge_lines=true`). bLLA иногда отрывает
первое слово строки в отдельный сегмент. Наши доработки:
* продолжение линии определяется по *направлению базовой линии* (`unit_direction`) и
  смещению вдоль неё, а масштаб берётся из **шага строк** (`estimate_pitch` — span
  середин базовых линий / число промежутков), а не из высоты контура: у волнистой строки
  контур может быть выше межстрочного расстояния, и первая версия склеивала лишнее;
* объединение через union-find, результирующий контур — выпуклая оболочка кусков
  (shapely), с четырёхугольником как запасным вариантом;
* эффект на первой странице: 45 сегментов → 36 (нейросеть) → 32 (после склейки),
  слов 200 → 199.

**Геометрия.**

* Для каждой строки и каждого слова хранится полигон (`htr_lines.polygon`,
  `htr_words.polygon`, JSON `[[x,y],…]`) плюс bbox как дешёвая оболочка.
* Слова нарезаются из текста по пробелам, а геометрия берётся из посимвольных «cut»
  kraken. Важная деталь: kraken для большинства символов отдаёт **позицию** в
  CTC-выравнивании (`_cuts[i] = [d, d]`), а не рамку. Поэтому слово режется от позиции
  первого символа до позиции символа *после* него (для последнего слова — до конца
  базовой линии, но с отступом: контур строки сходится в точку на конце, и сечение
  «до самого конца» вырождается в треугольник — отступ ищется шагами 2 px до 40 px,
  пока правая грань не станет не короче половины левой).
* Результат предсказания нормализуется в **NFC** (кодек модели хранит разложенные
  последовательности: `и` + U+0306 вместо `й`); для обучения текст приводится к **NFD**,
  иначе kraken считает `й`/`ё` новыми символами и пересоздаёт выходной слой со случайными
  весами.

**Конфигурация инференса:** `device=cuda:0` (с автоматическим откатом на CPU и
предупреждением), batch 8, padding 16, `text_direction=horizontal-lr`,
`num_line_workers=0` (извлечение строк в том же процессе).

**Декодирование.** Матрица CTC отдаётся kraken через
`RecognitionInferenceConfig(return_logits=True)`; `record.logits` имеет форму
`(classes, time)`, уже после softmax, `blank = 0`. По умолчанию работает
**prefix beam search** (`infrastructure/kraken/beam.py`) со символьной n-gram моделью
(порядок 6, Stupid Backoff) и мягким бонусом за слово из словаря:
`score = log P_ctc + α·log P_lm + β·слов + bonus·известных слов` (всё в log10).
Управляется `htr_decoder` (`beam`/`greedy`), ширина луча 32, top-k 8, α = 0.1.
Кодек модели — **NFD**, поэтому и LM, и лексикон строятся в NFD (иначе `й`, приходящий
как `и` + U+0306, был бы незнакомым символом). Если артефакта LM нет, в его алфавите нет
пробела или в нём меньше `htr_lm_min_text_chars = 1000` символов *реального* текста,
распознаватель молча возвращается к greedy — страница отдаётся всегда. Замер выигрыша —
§ 6.6.

**Уверенность.** Для каждого слова считается средняя посимвольная вероятность CTC;
пороги: `warning < 0.90`, `critical < 0.70` (настраиваются). Цвет на изображении:
серый контур / amber / красный.

**Скорость:** 67.6 с на страницу 3472×4640 (30 строк, 192 слова, 1137 символов) вместе
с загрузкой модели, на RTX 5060 Ti. Beam добавляет ≈1.1 с на строку (≈33 с на страницу)
при ширине 32 и ≈2.7 с при 60.

## 3. Данные и разметка

Жизненный цикл страницы: `UPLOADED → RECOGNIZED → EDITING → CONFIRMED`.
Обучающий корпус автора — **все подтверждённые страницы**; страницы можно удалять
(удалённая не попадёт ни в одно будущее обучение, уже обученные версии не трогаются).

Разделение текстов строгое, это ключевое решение:

| поле | кто пишет | роль |
| --- | --- | --- |
| `predicted_text` | kraken | распознавание, не меняется никогда |
| `suggested_text`, `suggested_by` | LLM | предложение правки, ждёт решения человека |
| `corrected_text`, `corrected_by` | пользователь | единственный эталон (правки руками и принятые предложения) |

Поэтому CER/WER и обучение никогда не видят невыверенный машинный текст.

**Словарная проверка (OOV).** При чтении страницы каждое слово помечается
`in_lexicon`, строки/страницы получают `oov_count`. Словарь — Bloom-фильтр 2.89 МБ
(2 409 933 словоформы + фамилии, MIT-список danakt/russian-words, 7 хеш-функций,
~2 МБ памяти). Слои: общий словарь + слова подтверждённых страниц автора + термины базы
знаний. Старая орфография обрабатывается как *дополнительные варианты* (`ѣ і ѳ ѵ`,
конечный `ъ`, `-аго→-ого`, `-ыя→-ые`, `-ія→-ие`, `ея→её`); не помечаются числа, даты,
односимвольные слова и слова через дефис с известными частями. Сиреневый цвет
зарезервирован за OOV, amber/red — за уверенностью.

**Калибровка** (`scripts/calibrate_htr_lexicon.py`, режим leave-one-page-out — страница
не участвует в своём же словаре): **2.4 %** слов подтверждённого текста отсутствуют в
словаре (38 из 1581; медиана по страницам 3 %, максимум 4 %). В топе пропусков смесь
реальных топонимов/диалекта (`Судиславль`, `Аленушкино`, `лежневку`) и **незамеченных
пользователем ошибок распознавания** (`зипил`, `сиравился`, `Сетояла`, `вышика`).
На сырых предсказаниях активной v12 доля OOV = **5.2 %** (10 из 192), и это почти
исключительно настоящие ошибки — то есть сиреневые метки имеют высокую точность.
У базовой модели на первых страницах было 14.6 %.

## 4. Обучение персональной модели

**Порт.** `HTRTrainer` — framework-independent интерфейс; реализация `KrakenTrainer`
работает через объекты конфигов kraken 7 (`kraken.train`), а не через CLI.

**Данные.** Для автора собираются все подтверждённые страницы. Каждая строка режется
**вдоль сохранённого контура** через `kraken.lib.segmentation.extract_polygons` — ту же
функцию, которой распознавание вырезает строки со страницы (базовая линия
восстанавливается из контура: контур — лента, её кромки разделяются по знаку смещения
от оси, пересэмплируются вдоль оси и усредняются). Прямоугольный кроп остался
фолбэком. Разбиение train/val — 90/10, детерминированное по seed. Хеш датасета
включает `page|line|transcription|дайджест контура`.

**Гиперпараметры по умолчанию** (все в `backend/app/config.py`): 10 эпох, batch 4,
lr 1e-4, cosine + warmup 10 шагов, weight decay 0.01, `resize=union`,
`normalization=NFD`, высота строки 96 (высота самого чекпойнта, см. § 6.7),
max width 2560, точность 32-true,
аугментация включена, `torch.compile` выключен, `num_workers=0`.

**Регуляризация против «катастрофического забывания»** (три отдельные меры):

1. `htr_training_freeze_backbone = -1` — backbone (всё, кроме проекции под кодеки)
   заморожен первую эпоху (`ceil(train_samples / batch_size)` шагов), затем учится вместе
   со всеми. Значение — в **шагах оптимизатора** (`trainer.global_step`), не в сэмплах.
2. `htr_training_freeze_bn = true` — статистики BatchNorm (61 слой) остаются в eval всю
   тренировку: батч из 4 кропов не может переоценить предобученные статистики.
3. `htr_training_aux_nrtr = false` — вспомогательная NRTR-голова kraken отключена
   (см. § 6, «что не сработало»).

**Гейт качества.** После обучения кандидат и **нетронутая базовая модель** измеряются на
одном и том же валидационном сплите. Если CER кандидата не лучше — версия помечается
`NO_IMPROVEMENT`, ничего не активируется, предыдущая активная модель остаётся. У автора
одна активная версия; есть скрипт ручного отката.

**Порог.** Обучение запускается автоматически при подтверждении страницы, но не раньше
50 подтверждённых строк (иначе `INSUFFICIENT_DATA`).

**Скорость:** ~170–210 с на прогон (212 строк, 10 эпох, batch 4). Обучение синхронно
внутри HTTP-запроса подтверждения (страница → обучение → активация ≈ 4 минуты); сервис
HTTP-агностичен и может быть вынесен в воркер без изменения API.

**История версий** (что и почему):

| версия | статус | причина |
| --- | --- | --- |
| v1 | FAILED | порт на API kraken 7 ещё не был готов |
| v2 | READY | первый успешный прогон (прямоугольные кропы, batch 8, lr 1e-4), валидация 0.216 |
| v3, v4, v5 | FAILED | забывание: CER 0.38 / 0.21, у v5 совпал с базовой (0.2117) — на экспорт уходил чекпойнт нулевой эпохи, то есть фактически базовая модель |
| v6 | READY | после отключения NRTR-головы, заморозки BN и backbone: 0.135 против 0.212 |
| v7 | READY | первый прогон на кропах вдоль базовой линии: 0.046 против 0.089 |
| v8…v12 | READY/ACTIVE | каждый подтверждённый лист переобучает модель; v11 валидация 0.0236 |

## 5. Правки распознанного текста языковой моделью (gemma3:12b)

**Роль LLM — предлагать, а не править.** Модель никогда не пишет в транскрипцию:
её ответ сохраняется в `suggested_text` рядом со строкой. Дальше — диф и решение человека.

**Что попадает в промпт (Фаза 0, всё из уже накопленных данных):**

| часть | источник | сейчас |
| --- | --- | --- |
| лексикон автора | частотные слова подтверждённых страниц | 200 слов |
| confusion-профиль | выравнивание `predicted ↔ corrected` по символам | 25 пар (порог: встречаемость ≥ 2) |
| few-shot примеры | реальные пары «было / стало» этого автора | 5 |
| термины базы знаний | сущности, события, цели, привычки | 74 |
| соседние строки | ±2 строки как контекст, править их нельзя | — |

Фактический confusion-профиль сейчас (распознано → должно быть, с числом):
`о→а (16), х→к (8), м→л (7), й→т (5), и→п (5), н→и (5), е→а (4), л→м (4), я→л (4)`.

Правила промпта: исправлять только механические ошибки распознавания, не менять стиль,
орфографию, пунктуацию и структуру; при неуверенности оставлять как есть; выводить
ровно одну строку без пояснений. Параметры генерации: `temperature=0`, `top_p=0.9`,
`num_predict=256`, `keep_alive=10m`.

**Проверка ответа словарём.** Диф считается по словам, и каждое изменение получает
вердикт: **зелёный** — новое слово есть в общем словаре или в лексиконе автора,
**сиреневый** — такого слова нет нигде (здесь модель выдумывает), **серый** — проверять
нечем (словарь не установлен) или это удаление/склейка, которые словарь подтвердить не
может. Строка считается проверенной, только если **все** изменения зелёные.

**Режимы принятия.** Клик по отдельному чипу применяет **одно** слово (правка
вставляется по символьным смещениям, пунктуация и пробелы автора сохраняются);
«Принять всё» — строку целиком; «Принять проверенные (N)» — массово только те строки,
где все изменения зелёные; «Скрыть» — убрать предложение. Правка строки руками снимает
её предложение; подтверждение страницы очищает все предложения. Строки, которые
пользователь уже написал сам, моделью не трогаются.

**Склейки/разрывы слов** («на зывалось» → «называлось») распознаются как одно изменение
(если буквы совпадают), поэтому лечатся одним кликом и проверяются словарём; в остальных
случаях блок разбивается на замену + удаление, и потерянное слово видно отдельным чипом.

**Отказоустойчивость.** Санитайзер отбрасывает пустой, многострочный ответ и ответ,
отличающийся по длине более чем в 3 раза / менее чем в 0.34 раза. Две неудачи подряд —
прогон по странице прекращается (чтобы недоступная Ollama не стоила таймаута на каждую
строку). Автозапуск после распознавания выключен (`htr_correction_auto=false`).

**Метрики LLM-этапа.** Первый замер на 5 строках с правками пользователя (контекст был
пуст): CER 0.065 → 0.054, WER 0.383 → 0.334. На странице 3 после появления первого
подтверждённого листа: 24 предложения, из них **17 полностью проверенных словарём**;
49 с на страницу из 30 строк вместе с загрузкой модели, 0.3–0.7 с на строку после
прогрева (первый вызов 62 с).

**Наблюдаемые ошибки модели:** любит добавлять/переносить пунктуацию (предложения
«только пунктуация» принимаются лишь целиком); иногда переписывает слишком смело —
например `пазиі. организцни и. Судиславль` → `партийной организации.` с потерей
топонима (такое блокируется словарём); придумывает падежи (`Судиславль → Судиславле`,
`годе → года`). Удачные примеры: `ойца→отца`, `1д46→1946`, `Жизь→Жизнь`,
`пазиі→партийной`, `организоцни→организации`, `времся→время`, `зухнуло→утонуло`,
`натаи→найти`, `тогдо→тогда`.

**Журнал решений.** Каждое действие человека по предложению пишется в
`htr_suggestion_events`: `accepted_change` (одно слово), `accepted_line` (строка
целиком), `accepted_bulk` (массово проверенные), `dismissed` (скрыть), с текстом
предложения, фрагментом до/после и флагом «слово было в словаре». Запись
best-effort: сбой журналирования не ломает принятие правки. Потребителя у этих
данных пока нет — это заготовленный датасет для дообучения промпта и
confusion-профиля (см. § 8, п. 17).

### 6.4 Словарь и OOV

| | |

### 6.6 Beam search с языковой моделью против greedy (хронологические фолды)

Обе колонки — один и тот же вызов распознавания, отличаются только декодеры; эталон —
транскрипция пользователя. Акустическая модель — **базовая** (страницы ей незнакомы),
LM для каждой страницы собран только из **подтверждённых страниц с меньшим id**, то есть
из тех, что были подтверждены раньше: ровно то, что есть у системы к моменту
распознавания (поздние листы ещё не написаны). Более слабый вариант —
`--leave-one-page-out`, скрывающий только саму страницу. Ширина луча 32, top-k 8,
α = 0.1, β = 0, бонус за слово 0.8.

| страница | текста автора в LM | greedy CER | beam CER | greedy WER | beam WER |
| --- | --- | --- | --- | --- | --- |
| 3 | 0 | 0.0949 | 0.0949 (фолбэк на greedy) | 0.3015 | 0.3015 |
| 9 | 1 157 | 0.0654 | **0.0628** | 0.2438 | **0.2388** |
| 14 | 2 356 | 0.0612 | **0.0532** | 0.1900 | **0.1700** |
| 16 | 3 512 | 0.0884 | **0.0758** | 0.2850 | **0.2539** |
| 17 | 4 648 | 0.0896 | **0.0686** | 0.3298 | **0.2461** |
| 18 | 5 772 | 0.0776 | **0.0639** | 0.3033 | **0.2701** |
| 19 | 6 975 | 0.0697 | **0.0514** | 0.2576 | **0.1869** |
| 20 | 8 094 | 0.0564 | **0.0353** | 0.2552 | **0.1667** |
| **всего (239 строк)** | | 0.0753 | **0.0632** | 0.2707 | **0.2297** |

Вывод: beam выигрывает на каждой странице, где в модели есть хотя бы ~1 000 символов
реального связного текста, и выигрыш растёт с корпусом: −2 % относительного WER на
странице 9, −35 % на странице 20 и **−15 % в сумме по восьми страницам** (WER
0.2707 → 0.2297) — итог занижают первые страницы, у которых модели почти нет.
При нуле связного текста LM знает буквы, но не знает, что бывает после пробела, и
немного **проигрывал** greedy (страница 3), поэтому ниже порога
`htr_lm_min_text_chars = 1000` распознаватель принудительно использует greedy. Счёт идёт
по `running_text_chars`, а не по общему размеру корпуса: модель, собранная только из
словоформ, имеет миллионы символов и всё равно не умеет расставлять пробелы.

**Проверка боевого пути.** В проде распознаватель берёт `author_<id>_char_lm.npz`
(9 258 символов подтверждённого текста автора) и получает словарь автора как мягкий
бонус за слово; на той же странице 20 боевой путь (`_build_decoder` с настоящим кодеком,
Bloom-словарём и словами автора) даёт CER 2.73 % / WER 11.46 % против greedy
5.64 % / 25.52 %. Эти числа сознательно **не** в таблице: это повторное распознавание уже
подтверждённой страницы, и её текст законно лежит в LM. Проверка доказывает только то,
что путь собран целиком и словарь доходит до декодера.

**Оба протокола фолдов согласуются.** Тот же замер с буквальным
`--leave-one-page-out` (скрывается только сама страница) на тех же матрицах даёт
greedy CER 0.0753 / WER 0.2707 → beam CER 0.0622 / WER 0.2290 (+0.0131 CER, +0.0417 WER)
против +0.0121 / +0.0410 у хронологических фолдов. Различие ровно там, где и должно
быть: при leave-one-page-out в модели *первой* страницы лежат поздние страницы
(8 100 символов), поэтому она тоже улучшается (CER 0.0949 → 0.0851). Единственная
регрессия в обоих прогонах — страница 9 (WER 0.2438 → 0.2587). В таблице выше —
хронологические числа, потому что они описывают то, что у системы реально есть в момент
распознавания.

Две измеренные ловушки, каждая из которых превращала выигрыш в проигрыш:

* **словоформы без пробелов.** Синтетические «предложения» из 10 словоформ дали 28 млн
  символов фейковой межсловной статистики, которые утопили 0.3 млн символов реального
  текста автора: WER 0.37 против 0.27 у greedy. Связный текст — только настоящий;
* **утечка страницы в LM.** Артефакт, собранный со всеми страницами (в том числе с
  оцениваемой, с весом 30), показывал на странице 20 CER 5.64 % → 1.32 % и WER
  25.5 % → 5.7 % — это были её же слова. Числа в таблице выше утечки не содержат;
  воспроизводится через `scripts/measure_htr_decoders.py --chronological` (кэш
  матриц и фолдов переиспользуется ключом `--reuse-cache`).

### 6.7 Высота строки (96 против 128 px)

PP-OCRv6 предобучен на высоте 128, в конфиге проекта стояло 96 — это выглядело как
рассогласование масштаба. При этом экспортированный чекпойнт объявляет собственную
входную форму (`input=(1, 3, 96, 0)`), и kraken перезаписывает `config.height` значением
из чекпойнта, так что настройка до сети вообще не доходила. Замер на одном корпусе,
сплите и seed:

| прогон | запрошено | фактическая | val CER | val WER | base CER |
| --- | --- | --- | --- | --- | --- |
| A | из чекпойнта | 96 | 0.0303 | 0.1304 | — |
| A | 128 | 128 | 0.0325 | 0.1366 | — |
| B (`scripts/measure_htr_height.py`) | из чекпойнта | 96 | 0.0337 | **0.1366** | 0.0685 |
| B | 128 | 128 | 0.0337 | 0.1429 | 0.0685 |

Разброс между прогонами от стохастичности обучения (аугментация, порядок
редукций на CUDA) — около 0.003 CER, то есть того же порядка, что и сама разница.
Честный вывод: **128 нигде не лучше** (WER хуже в обоих прогонах, CER в одном равен,
в другом хуже), поэтому оставляем собственную высоту чекпойнта 96. Прогон B
воспроизводим, одинаковый base CER 0.0685 при обеих высотах подтверждает, что корпус
и сплит были одни и те же.

Механика: высота меняется только через явную опцию `htr_training_height_override`
(сама `htr_training_height` не работает — kraken перезаписывает `config.height`
значением из чекпойнта), а фактическая высота возвращается в
`training_metrics.line_height` (+`line_height_override_from` при принудительной) и
показывается в баннере обучения в UI.

## 8. Известные ограничения и открытые направления

**Метрики и валидация**
1. **Нет независимого holdout.** Все подтверждённые страницы входят в корпус, поэтому
   гейт сравнивает кандидата с базовой моделью на страницах самого автора
   (`holdout_used=false`). Вневыборочная кривая § 6.1 — единственная честная оценка.
   Резервирование целой страницы под оценку сделало бы гейт объективным.
2. Монитор чекпойнта использует accuracy kraken внутри обучения, а отчётный CER — наш
   тестовый путь с нормализацией (NFC/NFD): числа различаются (например 0.0314 против
   0.0325). Выбор «лучшей эпохи» оптимизирует не совсем ту метрику, что отчётная.
3. Валидация — 23 строки; это шумно (±1 строка ≈ 0.5 % CER).

**Распознавание**
4. Декодер — **prefix beam search** со символьной n-gram LM; он встроен в проект
   (`infrastructure/kraken/beam.py`), потому что `kenlm` не собирается на Python 3.13,
   а `pyctcdecode`/`torchaudio` недоступны. Kraken отдаёт матрицу вероятностей
   (`return_logits=True`), так что CTC-часть переиспользуется. Ограничение: словарь
   участвует только мягким бонусом за известное слово, а не жёстким ограничением
   (lexicon-constrained decoding не реализован).
5. Главная слабость LM — **корпус**: связного русского текста мало. Из доступного без
   сети нашлись только списки словоформ (2.4 млн форм) и подтверждённые страницы автора
   (0.3 млн символов); Gutenberg содержит 9 русских книг, Tatoeba и OPUS с этой машины
   throttled. Выигрыш beam растёт с корпусом (§ 6.6), поэтому подключение настоящего
   корпуса (`--extra-text`) — самый дешёвый способ улучшить распознавание дальше.
   Замеры сделаны на **базовой** акустической модели; beam поверх дообученной v12
   не измерялся.
6. Нет анализа макета страницы: колонки, порядок блоков, разделители не обрабатываются.
7. Склейка строк — эвристика (направление + шаг строк); при плотной волнистой строке
   возможны и лишние склейки, и пропущенные разрывы.
8. Геометрия слов у уже распознанных страниц не пересчитывается: правки в алгоритме
   действуют только на новые распознавания (пересчёт потребовал бы перераспознавания,
   а оно стирает правки пользователя).
9. bbox склеенных строк бывает вырожденным (наследие старого кода склейки) — на кропы
   обучения уже не влияет, но влияет на отображение и на фолбэк-кроп.

**Корпус и обучение**
10. 239 строк — очень мало. Аугментация — стандартная kraken, специальных искажений под
    тетрадный фон/наклон/росчерки нет.
11. Кропы — прямоугольные полосы вдоль базовой линии; перспективные искажения и
    выпрямление по дуге не применяются (модель ожидает именно полосы, поэтому это
    осознанный выбор).
12. Один автор = одна модель. Смешивание почерков не проверялось.

**Словарь**
13. Проверка не ловит осмысленные подмены (`карова`), опечатки с реальными словами и
    имена собственные, которых нет ни в словаре, ни в лексиконе автора.
14. Калибровка меряет только долю флагов на подтверждённом тексте; precision/recall
    флагов относительно реальных ошибок не измерялись.

**LLM-этап**
15. Термины базы знаний приходят с мусором из извлечения сущностей: в контекст попадают
    фрагменты вида `##ть`, `##дем`, `ака`, `до 2 час` — это шум в промпте.
16. Предложения «только пунктуация» нельзя принять по словам — только строку целиком.
17. Обратная связь **логируется, но не используется**: каждое принятое и отклонённое
    предложение пишется в `htr_suggestion_events` (`accepted_change` / `accepted_line` /
    `accepted_bulk` / `dismissed`, с текстом до и после и флагом «слово было в словаре»),
    но эти данные пока не влияют ни на промпт, ни на отбор примеров, ни на
    confusion-профиль. Это готовый датасет для следующего шага.
18. Контекст — только лексикон, confusion-профиль, примеры и ±2 строки. Смысловой
    контекст (тема страницы, имена из базы знаний в этой строке) не передаётся.
19. Всё синхронно в HTTP-запросе: обучение 3–4 минуты, правки 49 с на страницу; при
    росте корпуса потребуется воркер.
