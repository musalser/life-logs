# Распознавание рукописного текста (HTR): текущие технические решения и метрики

Документ описывает систему «как есть» на текущий момент: инференс (включая
beam-декодирование с языковой моделью), сегментацию, обучение персональной модели,
словарную проверку и правки языковой моделью. Предназначен для внешнего анализа:
где искать улучшения.

Дата срезa: корпус 8 подтверждённых страниц, активная модель v12.

---

## 1. Контекст

| | |
| --- | --- |
| Задача | распознавание рукописных дневников/записей (русский язык, XX век, курсив, тетради в клетку) |
| Владелец данных | один автор (пользователь), несколько почерков в перспективе |
| Железо | RTX 5060 Ti 16 ГБ, WSL2 |
| Стек | Python 3.13 + FastAPI + PostgreSQL + SQLAlchemy/Alembic, фронтенд Nuxt 3 (Tailwind) |
| HTR-движок | kraken 7.1.1, torch 2.14 (cu130), Lightning 2.6 |
| LLM | Ollama, `gemma3:12b` (Q4_K_M, 8.15 ГБ), режима thinking у модели нет |
| Объём корпуса | 8 страниц · 239 строк · 1576 слов · 142 строки с правками пользователя (59 %) |

Архитектура кода: `API → application → domain ← infrastructure`. kraken импортируется
только внутри `infrastructure/kraken/` и только лениво, поэтому приложение работает
без ML-бэкенда (распознавание тогда отвечает 422 с внятным текстом).

## 2. Распознавание (инференс)

**Модель.** Базовая — `ppocrv6_medium.safetensors` (PP-OCRv6 medium, 61 МиБ, ~15.9 млн
параметров, 1622 класса кодека). Загружается через kraken `load_safetensors(tasks=["recognition"])`.

**Сегментация.** По умолчанию нейросетевая — встроенная в kraken модель **bLLA**
(`SegmentationTaskModel`), даёт *полигоны*, следующие за изогнутой строкой, а не
прямоугольники. Есть резервный классический сегментер (`kraken.pageseg`, проекционный
профиль), включается настройкой `htr_segmentation_engine="classical"` или автоматически,
если нейросетевую не удалось загрузить (нужен `coremltools` для весов bLLA).

**Склейка разорванных строк** (`htr_segmentation_merge_lines=true`). bLLA иногда отрывает
первое слово строки в отдельный сегмент. Наши доработки:
* продолжение линии определяется по *направлению базовой линии* (`unit_direction`) и
  смещению вдоль неё, а масштаб берётся из **шага строк** (`estimate_pitch`), а не из
  высоты контура: у волнистой строки контур может быть выше межстрочного расстояния, и
  первая версия склеивала лишнее;
* высоты контуров всё же участвуют, но только как допуск кластеризации середин базовых
  линий; сам шаг — медиана расстояний между кластерами. Оценка `span / (n − 1)` считала
  *сегменты*, а не строки: на странице, которую сегментер разрезал на несколько кусков на
  строку (журнал тренировок автора «Тренер», где слова и числа стоят далеко друг от
  друга), шаг падал в число раз, равное числу кусков на строку, и порог склейки
  отбрасывал ровно те разрывы, которые должен был закрыть. На стр. 170 у 56 сырых
  сегментов «шаг» был 34 px и они оставались ~50 строками; после кластеризации шаг
  271 px и они склеиваются в 8 физических строк. У «me» и «Баба Гали» число строк
  не меняется (28–32);
* **физические строки по проекции чернил** (`htr_segmentation_rows=true`,
  `infrastructure/kraken/rows.py`): геометрическая склейка всё равно не может поставить
  кусок без направления — крошечный «+» между словами, номер на поле с почти вертикальной
  базовой линией. Горизонтальный профиль чернил отвечает на другой вопрос — где именно
  строки. Маска строится на уменьшенной до 1500 px копии: Otsu отделяет бумагу от стола,
  крупнейшая светлая область — страница, чернила — пиксели на 25 уровней темнее неё;
  профиль сглаживается на 1/150 высоты, полоса начинается там, где он превышает
  `htr_segmentation_rows_threshold` (0.4) от максимума. Полосы только **добавляют**
  склейки: геометрические группы считаются первыми, а затем объединяются те, что попали в
  одну полосу. Слишком широкая полоса может склеить две плотные строки, поэтому порог
  взят с запасом, а страницы дневника не меняются: у «me»/«Баба Гали» ни одна полоса не
  содержит двух строк (28–32 остаются), стр. 170 — 8 → **7** физических строк,
  стр. 171 — 10 → 9. Кусок, стоящий *внутри* более длинного, входит в контур, но не в
  базовую линию: зигзаг через него сбил бы кроп. Отключается `htr_segmentation_rows=false`;
* объединение через union-find, результирующий контур — выпуклая оболочка кусков
  (shapely), с четырёхугольником как запасным вариантом;
* порядок строк — **отдельный шаг**: сегментер нумерует базовые линии в том порядке, в
  котором нашёл области, и на журнале это ставило первую строку третьей. `reading_order`
  сортирует строки по вертикали до распознавания (`_merge_split_lines`); страницы проекта
  одноколоночные, поэтому XY-cut не делается. На стр. 170 семь склеенных строк идут
  сверху вниз;
* эффект на первой странице: 45 сегментов → 36 (нейросеть) → 32 (после склейки),
  слов 200 → 199.

**Геометрия.**

* Для каждой строки и каждого слова хранится полигон (`htr_lines.polygon`,
  `htr_words.polygon`, JSON `[[x,y],…]`) плюс bbox как дешёвая оболочка.
* Слова нарезаются из текста по пробелам, а геометрия берётся из посимвольных «cut»
  kraken. Важная деталь: kraken для большинства символов отдаёт **позицию** в
  CTC-выравнивании (`_cuts[i] = [d, d]`), а не рамку. Поэтому слово режется от позиции
  первого символа до позиции символа *после* него (для последнего слова — до конца
  базовой линии, но с отступом: контур строки сходится в точку на конце, и сечение
  «до самого конца» вырождается в треугольник — отступ ищется шагами 2 px до 40 px,
  пока правая грань не станет не короче половины левой).
* Результат предсказания нормализуется в **NFC** (кодек модели хранит разложенные
  последовательности: `и` + U+0306 вместо `й`); для обучения текст приводится к **NFD**,
  иначе kraken считает `й`/`ё` новыми символами и пересоздаёт выходной слой со случайными
  весами.

**Конфигурация инференса:** `device=cuda:0` (с автоматическим откатом на CPU и
предупреждением), batch 8, padding 16, `text_direction=horizontal-lr`,
`num_line_workers=0` (извлечение строк в том же процессе).

**Декодирование.** Матрица CTC отдаётся kraken через
`RecognitionInferenceConfig(return_logits=True)`; `record.logits` имеет форму
`(classes, time)`, уже после softmax, `blank = 0`. По умолчанию работает
**prefix beam search** (`infrastructure/kraken/beam.py`) со символьной n-gram моделью
(порядок 6, Stupid Backoff) и мягким бонусом за слово из словаря:
`score = log P_ctc + α·log P_lm + β·слов + bonus·известных слов` (всё в log10).
Управляется `htr_decoder` (`beam`/`greedy`), ширина луча 32, top-k 8, α = 0.1.
Кодек модели — **NFD**, поэтому и LM, и лексикон строятся в NFD (иначе `й`, приходящий
как `и` + U+0306, был бы незнакомым символом). Если артефакта LM нет, в его алфавите нет
пробела или в нём меньше `htr_lm_min_text_chars = 1000` символов *реального* текста,
распознаватель молча возвращается к greedy — страница отдаётся всегда. Замер выигрыша —
§ 6.6.

**Уверенность.** Для каждого слова считается средняя посимвольная вероятность CTC;
пороги: `warning < 0.90`, `critical < 0.70` (настраиваются). Цвет на изображении:
серый контур / amber / красный.

**Скорость:** 67.6 с на страницу 3472×4640 (30 строк, 192 слова, 1137 символов) вместе
с загрузкой модели, на RTX 5060 Ti. Beam добавляет ≈1.1 с на строку (≈33 с на страницу)
при ширине 32 и ≈2.7 с при 60.

## 3. Данные и разметка

Жизненный цикл страницы: `UPLOADED → RECOGNIZED → EDITING → CONFIRMED`.
Обучающий корпус автора — **все подтверждённые страницы**; страницы можно удалять
(удалённая не попадёт ни в одно будущее обучение, уже обученные версии не трогаются).

Разделение текстов строгое, это ключевое решение:

| поле | кто пишет | роль |
| --- | --- | --- |
| `predicted_text` | kraken | распознавание, не меняется никогда |
| `suggested_text`, `suggested_by` | LLM | предложение правки, ждёт решения человека |
| `corrected_text`, `corrected_by` | пользователь | единственный эталон (правки руками и принятые предложения) |

Поэтому CER/WER и обучение никогда не видят невыверенный машинный текст.

**Словарная проверка (OOV).** При чтении страницы каждое слово помечается
`in_lexicon`, строки/страницы получают `oov_count`. Словарь — Bloom-фильтр 2.89 МБ
(2 409 933 словоформы + фамилии, MIT-список danakt/russian-words, 7 хеш-функций,
~2 МБ памяти). Слои: общий словарь + слова подтверждённых страниц автора + термины базы
знаний. Старая орфография обрабатывается как *дополнительные варианты* (`ѣ і ѳ ѵ`,
конечный `ъ`, `-аго→-ого`, `-ыя→-ые`, `-ія→-ие`, `ея→её`); не помечаются числа, даты,
односимвольные слова и слова через дефис с известными частями. Сиреневый цвет
зарезервирован за OOV, amber/red — за уверенностью.

**Калибровка** (`scripts/calibrate_htr_lexicon.py`, режим leave-one-page-out — страница
не участвует в своём же словаре): **2.4 %** слов подтверждённого текста отсутствуют в
словаре (38 из 1581; медиана по страницам 3 %, максимум 4 %). В топе пропусков смесь
реальных топонимов/диалекта (`Судиславль`, `Аленушкино`, `лежневку`) и **незамеченных
пользователем ошибок распознавания** (`зипил`, `сиравился`, `Сетояла`, `вышика`).
На сырых предсказаниях активной v12 доля OOV = **5.2 %** (10 из 192), и это почти
исключительно настоящие ошибки — то есть сиреневые метки имеют высокую точность.
У базовой модели на первых страницах было 14.6 %.

## 4. Обучение персональной модели

**Порт.** `HTRTrainer` — framework-independent интерфейс; реализация `KrakenTrainer`
работает через объекты конфигов kraken 7 (`kraken.train`), а не через CLI.

**Данные.** Для автора собираются все подтверждённые страницы. Каждая строка режется
**вдоль сохранённого контура** через `kraken.lib.segmentation.extract_polygons` — ту же
функцию, которой распознавание вырезает строки со страницы (базовая линия
восстанавливается из контура: контур — лента, её кромки разделяются по знаку смещения
от оси, пересэмплируются вдоль оси и усредняются). Прямоугольный кроп остался
фолбэком. Разбиение train/val — 90/10, детерминированное по seed. Хеш датасета
включает `page|line|transcription|дайджест контура`.

**Гиперпараметры по умолчанию** (все в `backend/app/config.py`): 10 эпох, batch 4,
lr 1e-4, cosine + warmup 10 шагов, weight decay 0.01, `resize=union`,
`normalization=NFD`, высота строки 96 (высота самого чекпойнта, см. § 6.7),
max width 2560, точность 32-true,
аугментация включена, `torch.compile` выключен, `num_workers=0`.

**Регуляризация против «катастрофического забывания»** (три отдельные меры):

1. `htr_training_freeze_backbone = -1` — backbone (всё, кроме проекции под кодеки)
   заморожен первую эпоху (`ceil(train_samples / batch_size)` шагов), затем учится вместе
   со всеми. Значение — в **шагах оптимизатора** (`trainer.global_step`), не в сэмплах.
2. `htr_training_freeze_bn = true` — статистики BatchNorm (61 слой) остаются в eval всю
   тренировку: батч из 4 кропов не может переоценить предобученные статистики.
3. `htr_training_aux_nrtr = false` — вспомогательная NRTR-голова kraken отключена
   (см. § 6, «что не сработало»).

**Гейт качества.** После обучения кандидат и **нетронутая базовая модель** измеряются на
одном и том же валидационном сплите. Если CER кандидата не лучше — версия помечается
`NO_IMPROVEMENT`, ничего не активируется, предыдущая активная модель остаётся. У автора
одна активная версия; есть скрипт ручного отката.

**Порог.** Обучение запускается **вручную** кнопкой «Обучить модель» (в шапке
вкладки «Рукописи», выше селектора автора). Ограничение на размер корпуса
**отключено по умолчанию** (`htr_min_training_lines = 0`): подтверждение страницы —
это решение пользователя, что материал стоит учить, поэтому обучаем на любом
непустом корпусе. Порог можно вернуть настройками `htr_min_training_lines` /
`htr_min_training_words` — тогда при недоборе результат `INSUFFICIENT_DATA`;
пустой корпус (0 строк) отклоняется всегда, учить не на чем. Подтверждение
страницы обучение не запускает — иначе каждая подряд подтверждённая страница
стоила бы отдельного дообучения на несколько минут.

**Скорость:** ~170–210 с на прогон (212 строк, 10 эпох, batch 4). Обучение
синхронно внутри HTTP-запроса `POST /htr/authors/{id}/train`; сервис
HTTP-агностичен и может быть вынесен в воркер без изменения API.

**История версий** (что и почему):

| версия | статус | причина |
| --- | --- | --- |
| v1 | FAILED | порт на API kraken 7 ещё не был готов |
| v2 | READY | первый успешный прогон (прямоугольные кропы, batch 8, lr 1e-4), валидация 0.216 |
| v3, v4, v5 | FAILED | забывание: CER 0.38 / 0.21, у v5 совпал с базовой (0.2117) — на экспорт уходил чекпойнт нулевой эпохи, то есть фактически базовая модель |
| v6 | READY | после отключения NRTR-головы, заморозки BN и backbone: 0.135 против 0.212 |
| v7 | READY | первый прогон на кропах вдоль базовой линии: 0.046 против 0.089 |
| v8…v12 | READY/ACTIVE | каждый подтверждённый лист переобучает модель; v11 валидация 0.0236 |

## 3.21 Список с папками, действия — в транскрипции

Три панели «Рукописей» больше не называются: заголовки «Страницы», «Изображение» и
«Транскрипция» убраны — кнопка загрузки, легенда и кнопки действий говорят сами.
Кнопка загрузки переименована в **«Загрузить изображение»** (загружают файл, а в
списке живут страницы), и она единственная осталась в левой панели.

**Список сгруппирован по источникам.** Папка — это каталог из `source_path`. Имя
папки берётся с конца пути и **наращивается вверх, пока не станет уникальным**:
три папки `diary/1975`, `letters/1975` и `archive/letters/1975` показываются
именно так, а не тремя «1975». Заголовок папки — кнопка: щелчок скрывает или
показывает её страницы (`aria-expanded`), счётчик стоит в заголовке. Страницы без
источника (их выбирают обычным файловым диалогом) идут первыми, без заголовка —
это не «папка с пустым именем», а просто страницы.

![Список с папками](screenshots/manuscripts-folders.png)

**Действия переехали к тексту.** «Распознать заново» и «Подтвердить страницу» —
суждения о транскрипции, а не о скане, поэтому они стоят в панели текста, над
строками. Туда же переехала «Принять проверенные»: она делает то же самое — меняет
текст по решению пользователя.

![Действия в панели транскрипции](screenshots/manuscripts-transcription-actions.png)

Что пришлось решить по дороге:

* **Перетаскивание работает, пока список — один ряд строк.** Порядок на сервере
  один на автора, и внутри папок перетаскивание между группами не имеет
  однозначного смысла: страница вернулась бы в свою папку. При нескольких группах
  ручки перетаскивания не показываются (`canReorder`), при одной — работают как
  раньше.
* **Открытие страницы раскрывает её папку** (`watch(page)`): скрытая папка не
  должна прятать ту страницу, которая сейчас открыта.
* **Свёрнутость живёт в памяти** и не переживает перезагрузку: состояние списка —
  не то, что стоит хранить между сессиями.

Проверено в браузере на синтетических данных (шесть страниц с путями, созданных
через API и удалённых после):

```
папки: diary/1975 (2), letters/1975 (2), archive/letters/1975 (1)
строк: 20, первые — без папки ("Стр. #26", "Стр. #24", …)
заголовков панелей в DOM: []          (все три убраны)
кнопки панели транскрипции: ["Распознать заново", "Подтвердить страницу"]
это самая правая из 2 панелей: true
ручек перетаскивания при группировке: 0
скрыть "letters/1975": строк 20 → 18; показать снова: 18 → 20
```

Сегодня **ни у одной страницы в базе нет `source_path`** (папкой больше не
загружают), поэтому список выглядит плоским, пока источники не появятся: либо
через API с `source_path`, либо если вернуть загрузку папкой — это один `<input>`
рядом с существующим.

## 3.20 Одно имя из одного источника — одна страница

Страница опознаётся парой «имя + источник»: одинаковые имена из **разных** папок —
это две страницы (ровно для этого `source_path` и хранится), а то же имя из того же
источника — это одна и та же страница, загруженная дважды, то есть дубль в корпусе,
а не новая запись. Такой upload отклоняется.

Правило живёт на бэкенде (`HandwritingPageService.upload_page` →
`DuplicatePageError` → HTTP 409) и повторено на клиенте, чтобы скан на 7 МБ не ехал
по сети ради отказа. Сравнение имён — без учёта регистра и краевых пробелов
(`Page.JPG` и `page.jpg` — один файл на любой файловой системе, из которой браузер
читает); пути нормализуются к прямым слэшам. Проверка на сервере идёт **до** записи
изображения, поэтому отказ не оставляет осиротевшего файла.

Краевые случаи, закреплённые тестами (`tests/test_htr_routes.py`):

| случай | ответ |
| --- | --- |
| то же имя, тот же путь | 409 |
| то же имя без пути (обычный выбор файла) | 409 |
| `  page.jpg  ` после `Page.JPG` | 409 |
| то же имя из другой папки | 201, две страницы |
| то же имя у другого автора | 201 |
| то же имя после удаления страницы | 201 |

В интерфейсе отказ виден красной плашкой: «Страница «205150.jpg» уже загружена из
этого источника» — иначе выбор файла выглядел бы как «ничего не произошло».

![Отказ на дубль имени](screenshots/duplicate-name-refused.png)

Два следствия, которые пришлось закрыть:

* **`uploading` держится до конца всего цикла**, включая автозапуск распознавания.
  Между «байты сохранены» и «модель начала читать» есть секунда-другая, и второй
  upload, выбранный в этот промежуток, потерял бы своё сообщение, когда первый
  цикл дойдёт до `clearMessages()`. Кнопка поэтому выключена весь цикл, а её
  надпись смотрит на `recognizing` первым, чтобы не писать «Загрузка…», пока идёт
  распознавание;
* **`recognize()` защищён от параллельного запуска** (см. 3.19).

Тесты, поднимавшие две страницы одного автора через `run_page_cycle("page.png")`,
теперь называют их по-разному — правило запрещает именно то, что они делали по
недосмотру, а не то, что они проверяли.

Граница правила: оно про **загрузку**. Переименование страницы (PATCH
`/htr/pages/{id}/name`) по-прежнему может дать два одинаковых имени — это осознанное
действие с мгновенной обратной связью в списке, где такие строки показываются полным
путём (`duplicateFileNames`). Если дубли надо запрещать и там, это отдельный вызов
`find_page_by_name` в `rename_page`.

Проверено на живом бэкенде (временный инстанс на :8001, та же Postgres):

```
POST /htr/authors/1/pages  (файл)                 → 201, page 145
POST /htr/authors/1/pages  (тот же файл)          → 409, "Page 'test-page-small.jpg'
                                                      from this source is already uploaded (page 145)"
POST … + source_path=album/1975/<то же имя>       → 201, page 146
```

и в браузере, на реальном потоке: тот же файл, выбранный второй раз после того, как
кнопка снова стала активной, даёт одну POST-запись вместо двух, 15 страниц вместо 16
и красную плашку с именем файла; файл с другим именем загружается как обычно.
Обе тестовые страницы удалены, в базе снова 14 страниц.

## 3.19 Загрузка живёт в списке страниц и распознаётся сама

Кнопка «Загрузить папку» убрана, а «Загрузить страницу» переехала из шапки в панель
«Страницы» — туда, где страница и появляется. Шапка теперь про автора и обучение,
список — про страницы; пустое состояние «Страниц пока нет» стоит рядом со своим
действием. Логика загрузки не менялась: `onUpload` по-прежнему принимает список
файлов и умеет `source_path`, так что вернуть загрузку папкой — это добавить один
`<input>`, а не восстанавливать обработчик.

Загруженная страница не имеет разметки вообще, и единственное, что с ней можно
сделать, — прочитать её. Поэтому после выбора новой страницы `onUpload` сам зовёт
`recognize()`; кнопка «Распознать» остаётся для повторного запуска и для случаев,
когда распознавание упало.

Пока модель читает, скан **не исчезает, а блюрится** (`filter: blur(7px)`,
`opacity: .7`), поверх — кольцо-спиннер и «Распознавание…»:

![Распознавание: скан под блюром и спиннер](screenshots/recognition-busy.png)

Читатель не теряет место на странице, которое отнял бы полноэкранный спиннер: кадр
остаётся на месте, меняется только его резкость. Оверлей заодно перехватывает клики
по словам — открывать альтернативу слова, которое модель прямо сейчас переписывает,
нечего.

Две вещи, которые пришлось закрыть вместе с автозапуском:

* **кнопка загрузки выключена, пока идёт распознавание** («Дождитесь распознавания
  текущей страницы») — раньше загрузить вторую страницу можно было в любой момент,
  а теперь это сразу запустило бы второй прогон;
* **`recognize()` защищён ранним выходом** — два параллельных прогона подрались бы
  за `page`: более медленный ответ вернул бы в просмотрщик свою страницу, а флаг
  `recognizing` погасил бы спиннер, когда закончится первый из них.

Блюр — статичный фильтр на неподвижном кадре, и жесты, которые его двигали бы
(колесо, перетаскивание), на время распознавания отключены: перерисовывать фильтр
каждый кадр — ровно то, что делает медленную машину ещё медленнее.

Проверено на живой загрузке (1400×1048, 31 строка, распознавание 35 с): страница
создана и выбрана, `POST /htr/pages/136/recognize` ушёл сам, во время прогона
`viewer-busy` и `viewer-content--busy` на месте, кнопка загрузки уже пишет
«Загрузить страницу» (то есть `uploading` снят вовремя) и `disabled`, после
завершения — 31 строка текста и никаких ошибок.

## 3.18 Строка транскрипции — просто текст

Окно транскрипции читается как страница, а не как список карточек: у строки больше нет
рамки, фона, скругления и **цветной кромки слева** (ею показывалась уверенность строки —
это число читателю ничего не давало, потому что рядом уже есть цвет самих слов). Что
осталось и что появилось вместо:

* уверенность **слов** — по-прежнему цвет и жирность самих слов (жёлтый/красный —
  сомнение, фуксия — нет в словаре, фиолетовый пунктир — слово автора);
* активная строка — тонкая (2px) полоса слева у самого текста, без рамки и без
  изменения раскладки; при наведении и фокусе строка чуть подсвечивается фоном;
* копирование и удаление строки — две иконки в конце строки, прозрачные, пока на
  строку не наведён курсор (`pointer-events: none` у невидимых кнопок, иначе они
  перехватывают клик, который должен ставить каретку);
* три состояния строки — **иконки** в конце строки вместо чипов под ней: янтарный
  треугольник «разметка устарела» (объяснение — в подсказке), акцентная искра
  «у модели есть предложение», кружок «сохранение…». Устаревшая разметка и предложение
  видны всегда: это состояния, требующие решения, а решение, которого не видно, не
  принимают;
* подтверждённая страница (текст заморожен) помечена не пунктирной рамкой, а пунктирным
  подчёркиванием самого текста;
* варианты слова (чтения, которые рассматривал декодер) — **плавающий слой прямо под
  выбранным словом**, поверх следующей строки: клик по слову открывает его там, где
  слово стоит, и текст под слоем не сдвигается. Раньше панель была блоком под своей
  строкой: она толкала следующие строки вниз и оказывалась далеко от слова, а из-за
  узкой колонки четыре варианта разъезжались на две строки. Место под слово берётся по
  его символам (`Range`), а не по `mark`: метка есть только у сомнительных и незнакомых
  слов, у обычного слова измерять нечего. Слой следует за словом при прокрутке списка
  (иначе уезжает от него) и прячется при уходе курсора; ширина — до 24 rem. Закрывается
  он тремя способами: выбранным чтением (сразу, не дожидаясь сохранения), крестиком и
  **кликом вне слоя** — причём этот клик-закрытие проглатывается, чтобы не открыть
  варианты слова, по которому он пришёлся: следующее нажатие открывает их. Иначе после
  клика по слову приходилось искать крестик, чтобы просто уйти;
* подсказка по слову — **всплывающая карточка над словом**: появляется через 160 мс
  после того, как курсор остановился на слове (проход мышью по тексту карточек больше не
  поднимает), исчезает сразу; центрируется по слову, при нехватке места сверху
  переворачивается под слово, по горизонтали не выходит за края окна и остаётся над
  панелью транскрипции, а не над сканом. Карточка `pointer-events: none` — иначе она
  съедала бы клик, который ставит каретку. Анимация — только прозрачность (120 мс),
  без масштаба: масштаб менял измеренную ширину карточки на ~14 px, и центрирование
  считалось от неверного числа.

Двухслойная схема не изменилась (текст рисует слой, `textarea` прозрачна и владеет
кареткой и выделением) — оформление строки живёт снаружи неё. Снимки: `docs/screenshots/prose-dark.png`,
`prose-light.png`, `prose-tooltip.png`, `prose-alternatives-dark.png` / `prose-alternatives-light.png`.

## 3.9 Подтверждение страницы обратимо

Подтверждение перестало быть дорогой в одну сторону. `POST /htr/pages/{id}/reopen`
переводит страницу из `CONFIRMED` назад в `EDITING`: текст и правки сохраняются и
снова редактируются, а страница выходит из эталонного корпуса — следующий прогон
обучения её не увидит, и её слова перестают считаться словами автора (кэш корпуса
инвалидируется сразу). Метрики подтверждения (`prediction_cer`/`wer`) и
`confirmed_at` очищаются: они описывали замороженный текст, а не страницу сейчас.

Что откат **не** может: «разучить» уже обученную модель. v13 сохраняет всё, что
успела выучить; на состав следующих прогонов откат влияет, на прошлые —
нет. Артефакты языковой модели пересобираются в момент следующего обучения
(`htr_training_rebuild_lm`), а не при каждом откате: сборка читает десятки
миллионов символов и занимает около минуты. Операция запрещена, пока идёт
обучение автора, — иначе прогон читал бы корпус, меняющийся у него под руками.

В интерфейсе это один замок: открытый подтверждает страницу, закрытый возвращает
её в редактирование (с диалогом о последствиях), и такой же замок есть в списке
страниц. Кнопка запуска правок LLM («Предложить правки») из интерфейса убрана,
эндпоинт остался, а уже сохранённые предложения продолжают показываться.

## 3.17 Источники словаря автора

У словаря ровно два источника: **русский словарь** (2.4 млн форм) и слова
**подтверждённых** страниц автора — причём в панели показываются только те из них,
которых в русском словаре нет (слово, известное словарю, ничего не меняет). Поэтому у
автора без подтверждённых страниц панель **пуста**, сколько бы страниц ни было
загружено.

**База знаний источником не является** — и это было неверно дважды. Во-первых, её
термины приходят не из рукописи, а из дневникового пайплайна, поэтому у автора без
подтверждений список всё равно появлялся. Во-вторых, тот пайплайн сохраняет куски
WordPiece: замерено — из 81 сущности **35 оказались обрывками** (`##ang`, `##отчик`,
`##овского`, `Gol`, `Vu`, `Prom`, `##eus Grafana` рядом с `Golang`, `Vue`,
`Prometheus`, `Grafana`), из-за чего фрагменты вроде `ang`, `sk`, `vu` считались
известными русскими словами. Для подсказок языковой модели словарь знаний по-прежнему
используется (`CorrectionContextBuilder`) — он просто не словарь.

Функциональность «объявить слово не-словом» тоже убрана: она перекрывала общий
словарь (замерено: «иро» — реальное вхождение в списке на 2.4 млн форм), но словарь
должен быть языком, а не личным чёрным списком. Таблица `htr_lexicon_ignore` оставлена
как есть, её никто не читает.

## 3.16 100 % — это «вписано в окно»## 3.16 100 % — это «вписано в окно»

Процент масштаба теперь **относительный**: 100 % означает «страница целиком помещается
в окно». Дневниковый скан шириной ~3000 px в колонке ~700 px — это 24 % натуральной
величины, и такое число ничего не говорит читающему. Абсолютный масштаб остался тем,
чем живут трансформация и толщины обводок; пересчитан только ярлык, а база
пересчитывается при смене изображения или размера окна (вписанный вид остаётся
вписанным при изменении окна и по-прежнему показывает 100 %). Страница открывается
вписанной и отцентрованной, двойной клик возвращает к тем же 100 %, колесо zoom-ит
вокруг курсора, бейдж появляется только на время изменения. Снимок —
`docs/screenshots/viewer-fit-100.png`.

## 3.15 Масштаб по умолчанию и бейдж

Страница открывается в масштабе **100 %** (своё разрешение изображения), а не
подогнанной по ширине: раньше в углу висело «28 %» — величина, которая ничего не
значит для читающего. Подогнать по ширине по-прежнему можно двойным кликом. Процент
показывается **только пока масштаб меняется**: колесо или подгонка включают бейдж, и
через ~1.1 с после остановки анимации он плавно растворяется. Замерено: после
загрузки страницы масштаб 1.0 и прозрачность бейджа 0; во время прокрутки «124 %»,
через 1.7 с — снова 0.

## 3.14 Плавный зум изображения

Колесо больше не двигает масштаб напрямую: оно двигает **цель**, а один цикл
анимации подтягивает к ней видимый масштаб (`1 - exp(-dt / 90 мс)`, то есть
одинаково на 60 и 144 Гц). Точка под курсором — якорь, и смещение пересчитывается из
неё на каждом кадре, поэтому рукопись растёт вокруг курсора, а не уезжает от него:
замерено — один щелчок даёт 15 разных значений масштаба за 34 кадра при смещении
якоря на 0.1 px, шесть щелчков подряд дают ровно накопленный коэффициент (×2.46).
Толщины обводок идут за зумом через CSS-переменную на `<svg>` (а не через привязку к
каждому полигону), так что кадр анимации обновляет один элемент вместо сотен.
Перетаскивание отменяет анимацию (чтобы не спорить с указателем), при
`prefers-reduced-motion` зум мгновенный, а двойной клик так же плавно возвращает
подгонку по ширине, заканчиваясь ровно на смещении ноль.

## 3.12 Разгруженная карточка строки

Номер строки, «confidence N%» и счётчик «не в словаре: N» убраны: уверенность стала
**цветной кромкой слева** (спокойный зелёный → янтарный → красный), номер строки живёт
в подсказке кромки, а «не в словаре» — это цвет самих слов: фиолетово-фуксиевые жирные
неизвестные слова и фиолетовые жирные с пунктиром — слова автора. Иконки копирования и
удаления переехали в узкую колонку справа от поля, поэтому у карточки больше нет шапки:
вторую строку добавляют только состояния, требующие действия (предложение модели,
устаревшая разметка, идущее сохранение). На странице из 29 строк это дало 11.2 видимых
строк вместо 8.2.

Технически текст рисует слой, а textarea над ним прозрачна и владеет только кареткой и
выделением. Два следствия, которые пришлось выяснить на практике:

* **шрифт поля — моноширинный**. В пропорциональном жирное слово слоя шире, слой
  переносит строку раньше, метка уезжает на обрезанную вторую строку, а каретка (её
  браузер считает по раскладке textarea) попадает на другое слово — замерено: клик по
  «минингита)» ставил каретку на первое слово строки. В моноширинном начертании ширина
  жирного и обычного совпадает, и раскладки слоёв сходятся посимвольно;
* браузер красит выделенный текст своим цветом, из-за чего буквы двоились поверх
  цветного слова — поэтому у поля задан прозрачный `::selection`, и блок выделения
  принадлежит textarea, а буквы — слою;
* в тексте теперь видно **и уверенность**: слово ниже порога «сомнение» — янтарное,
  ниже «плохо» — красное, цвет несёт самый сильный сигнал (плохо → сомнение → нет в
  словаре → слово автора), а второй сигнал остаётся подчёркиванием (сомнительное
  слово не из словаря — янтарный текст с фуксиевым подчёркиванием). У подсвеченных
  слов есть подсказка при наведении («нет в словаре — проверьте слово · уверенность
  77 % — ниже порога 0.9»), а клик по ним выделяет слово и показывает варианты —
  как и клик по слову на скане. Метки — единственная часть слоя, принимающая
  указатель (`pointer-events: auto`), остальное поле по-прежнему ставит каретку;
* растущее поле обязано быть `overflow: hidden`: на Windows классическая полоса
  прокрутки появляется от переполнения в один пиксель, отнимает ~17 px ширины, текст
  переносится на строку дальше, и полоса остаётся навсегда — текст обрезался, а поле
  становилось выше содержимого. На Linux полосы оверлейные и баг не виден, поэтому
  проверка — инвариант (`scrollHeight <= clientHeight` для каждой строки).

Эталонные снимки — в `docs/screenshots/`.

## 3.11 Что подтверждение добавляет в словарь и как найти слово в тексте

Подтверждение — это и есть момент, когда слова страницы попадают в словарь автора,
поэтому о них сообщается **до** записи. Кнопка «Подтвердить страницу» открывает
модальное окно, которое спрашивает `GET /htr/pages/{id}/confirmation-preview` —
read-only двойник записи, возвращающий те же два списка: всё, что страница
добавила бы, и подмножество, которого **не знает общий словарь** (ровно то, что
перестанет подсвечиваться как неизвестное). В окне — счётчики и второй список
чипами; пишет только `POST .../confirm`, и после подтверждения слова больше не
показываются: отчёт принадлежал решению.

`preview_confirmation` и `confirm_page_report` делят `_dictionary_delta`, так что
предпросмотр обещает ровно то, что сделает запись. Проекция словаря —
`SqlAlchemyAuthorCorpus.author_words_with_page`: страница-кандидат проходит те же
правила переносов, что и сохранённая; проверка строится на **проектируемом**
словаре (`SqlAlchemyLexiconProvider.checker_with_words`), иначе слова под review
выглядели бы неизвестными, а не своими.

Каждое слово в окне кликабельно: место ищется прямо на странице
(`showPreviewWord`), ведь в словаре автора слова ещё нет — клик открывает строку и
ставит курсор на слово, его можно исправить сразу (окно при этом закрывается, иначе
оно закрыло бы саму строку). После подтверждения места вхождения
(`page_id`, `line_id`, `line_order`, `surface`) хранит панель словаря, и они
собираются только для слов, которых нет в общем словаре (для каждого «и» это было
бы бессмысленно), до 8 мест на слово.

Возврат подтверждённой страницы в редактирование — тоже модальное окно
(`REOPEN_CONSEQUENCES`): последствия списком, а не стеной текста в native
`confirm()`.

Варианты написания в отчёт не попадают: подтверждение «еврея» тянет за собой
служебный вариант «евреё» по правилу старых окончаний, и отчёт, в котором есть
слово, которого никто не писал, проверить глазами нельзя. На текущем корпусе в
панели 142 слова, у 47 есть места, слов без места нет.

## 3.10 Переносы слов и лексикон автора

Дневник рвёт слова на правом краю, а распознавание идёт построчно, поэтому в словарь
автора попадали обе половины: «слуша-» + «лась», «звакуи» + «ровать», «рела»,
«лись». Это не слова, и они приучали подсветку OOV считать осколок словом. Решение —
`domain/text.py::line_break_analysis`, и ему нужны **два разных сигнала**, потому что
словарь не отвечает ни на один из вопросов надёжно:

* **склейка — это слово?** — общий словарь (Bloom): и случай с дефисом («слуша-» +
  «лась» → «слушалась»), и одна ошибка распознавания («зажитог» + «ным» →
  зажиточным, «звакуи» + «ровать» → эвакуировать). Ошибки проверяются только на
  **шве** и на первой букве осколка — там, где они действительно бывают;
* **половина — самостоятельное слово?** — сам корпус, а не словарь: форма, которая
  встречается где-то **внутри** строки, — слово («ямы», «было», «она»), а форма,
  которая всегда стоит на краю строки, — нет. Спрашивать словарь нельзя: он отвечает
  «да» примерно одному случайному набору букв из ста и содержит морфемы («ным»,
  «ровать»), так что «ямыво» и «онане» прошли бы как слова.

Текст при этом не переписывается — строки остаются как распознаны; исправляется
только словарь: обе половины уходят из `author_words` (кроме случая, когда половина —
настоящее слово, например «строительном»), а склеенная форма в него входит, так что
полное слово становится известным. Склейка, найденная только через ошибку
распознавания, не добавляется: в ней сидит та же ошибка, и текст должен править
человек.

Замер на текущем корпусе (12 подтверждённых страниц, 351 строка): найдено 12
переносов, убрано 17 форм-осколков, добавлено 9 полных слов — включая «лась»,
«лись», «рела» и «звакуи». Один перенос из двенадцати — ложный («пастбища» +
«стадо»): Bloom отвечает «да» на «настбищастадо» примерно раз в 2500 проверок.
Второй фильтр с другой солью убрал бы это; цена пока — одно настоящее слово,
ушедшее из словаря.

## 4.0 Геометрия слов, когда beam и greedy разошлись в токенизации

Beam и собственный greedy-декодер kraken не всегда режут строку одинаково: дневниковая
строка `где -то` вернулась из beam как `где-то`. Посимвольные «cut»-ы описывают **greedy**-текст,
поэтому при несовпадении числа слов разметка слов выбрасывалась целиком — корректная
транскрипция без единого бокса, что выглядит как баг интерфейса. На странице 26 в таком
состоянии были 2 строки из 29.

Теперь текст-для-показа и greedy-текст выравниваются **посимвольно**
(`domain/text.py::map_spans_to_reference`), и каждое слово получает свой отрезок
референса: слияние покрывает оба greedy-слова, разбиение даёт каждой половине свой кусок,
замена буквы отображается на изменённый символ, а вставленное beam-ом слово остаётся без
геометрии — но **только оно**, остальная строка сохраняет боксы. Если не удалось построить
ни одного слова, строка теперь пишет об этом в лог, а не молчит.

Страницы, распознанные до фикса, свою разметку не пересчитывают (геометрия выводится из
CTC-матрицы, а она не хранится). Для них есть служебный скрипт
`scripts/repair_htr_word_geometry.py`: он заново распознаёт изображение страницы,
сопоставляет записи со строками (по геометрии, а при другой сегментации — по тексту) и
вставляет недостающие строки `htr_words`, отображая геометрию на **сохранённый** текст,
чтобы не тронуть правки пользователя. Применён к стр. 22 (строка 23) и стр. 26 (строки
23, 26) — по корпусу таких строк больше нет.

## 4.1 Альтернативы распознавания по словам (клик по слову)

Beam-декодер и так строит N-best строки, поэтому «другие чтения» каждого слова
получаются из него бесплатно: гипотезы выравниваются по словам
(`difflib.SequenceMatcher`), и варианты, различающиеся в одном слове, становятся
списком альтернатив этого слова (топ-5, отсортированы по оценке строки).
Ловятся и слияния/разбиения: `на зывалось → называлось` предлагается как один
вариант. Список пишется один раз при распознавании (`htr_words.alternatives`),
потому что выводится из CTC-матрицы, которая не хранится, и показывается в
карточке строки по клику на слово; клик по варианту подставляет его в текст.

Пример на реальной странице (v13): `вечерам → Вечерам, вечером`,
`девчонки → девгонки`, `а → А, я, и, о`, `завидовали. → заведовали.`.

**Ограничение — принципиальное:** в списке только то, что рассматривал beam.
Слова, которого акустика не выдала ни в одной гипотезе (редкая фамилия,
диалектное написание), там не будет — для этого остаются словарная проверка и
предложения LLM. Плюс: альтернатив нет у страниц, распознанных до появления
функции, нет при выключенном beam и нет на классическом (bbox) сегментаторе —
там kraken не прикладывает матрицу вообще (`BBoxOCRRecord.logits` — список
посимвольных кортежей), и распознавание честно откатывается на greedy.

## 5. Правки распознанного текста языковой моделью (gemma3:12b)

**Роль LLM — предлагать, а не править.** Модель никогда не пишет в транскрипцию:
её ответ сохраняется в `suggested_text` рядом со строкой. Дальше — диф и решение человека.

**Что попадает в промпт (Фаза 0, всё из уже накопленных данных):**

| часть | источник | сейчас |
| --- | --- | --- |
| лексикон автора | частотные слова подтверждённых страниц | 200 слов |
| confusion-профиль | выравнивание `predicted ↔ corrected` по символам | 25 пар (порог: встречаемость ≥ 2) |
| few-shot примеры | реальные пары «было / стало» этого автора | 5 |
| термины базы знаний | сущности, события, цели, привычки | 74 |
| соседние строки | ±2 строки как контекст, править их нельзя | — |

Фактический confusion-профиль сейчас (распознано → должно быть, с числом):
`о→а (16), х→к (8), м→л (7), й→т (5), и→п (5), н→и (5), е→а (4), л→м (4), я→л (4)`.

Правила промпта: исправлять только механические ошибки распознавания, не менять стиль,
орфографию, пунктуацию и структуру; при неуверенности оставлять как есть; выводить
ровно одну строку без пояснений. Параметры генерации: `temperature=0`, `top_p=0.9`,
`num_predict=256`, `keep_alive=10m`.

**Проверка ответа словарём.** Диф считается по словам, и каждое изменение получает
вердикт: **зелёный** — новое слово есть в общем словаре или в лексиконе автора,
**сиреневый** — такого слова нет нигде (здесь модель выдумывает), **серый** — проверять
нечем (словарь не установлен) или это удаление/склейка, которые словарь подтвердить не
может. Строка считается проверенной, только если **все** изменения зелёные.

**Режимы принятия.** Клик по отдельному чипу применяет **одно** слово (правка
вставляется по символьным смещениям, пунктуация и пробелы автора сохраняются);
«Принять всё» — строку целиком; «Принять проверенные (N)» — массово только те строки,
где все изменения зелёные; «Скрыть» — убрать предложение. Правка строки руками снимает
её предложение; подтверждение страницы очищает все предложения. Строки, которые
пользователь уже написал сам, моделью не трогаются.

**Склейки/разрывы слов** («на зывалось» → «называлось») распознаются как одно изменение
(если буквы совпадают), поэтому лечатся одним кликом и проверяются словарём; в остальных
случаях блок разбивается на замену + удаление, и потерянное слово видно отдельным чипом.

**Отказоустойчивость.** Санитайзер отбрасывает пустой, многострочный ответ и ответ,
отличающийся по длине более чем в 3 раза / менее чем в 0.34 раза. Две неудачи подряд —
прогон по странице прекращается (чтобы недоступная Ollama не стоила таймаута на каждую
строку). Автозапуск после распознавания выключен (`htr_correction_auto=false`).

**Недоступная Ollama отваливается быстро и явно.** Раньше на подключение и на генерацию
был один общий таймаут 90 с, а остановленная Ollama за Windows-фаерволом не отказывает в
соединении, а молча роняет пакеты — в итоге страница возвращалась через три минуты с
неопределённым «модель не предложила правок (или недоступна)». Теперь: connect-таймаут
отделён от генерации (`htr_correction_connect_timeout_s = 5`), перед прогоном делается
дешёвая проверка доступности (`GET /api/tags`), и при недоступности роут сразу отдаёт
`503` с адресом («Ollama недоступна по адресу … — запустите её и повторите»), не трогая
ни одну строку. Замер на «чёрной дыре»: 5.5 с на проверку и 5.0 с на попытку вместо
90 + 90.

**Метрики LLM-этапа.** Первый замер на 5 строках с правками пользователя (контекст был
пуст): CER 0.065 → 0.054, WER 0.383 → 0.334. На странице 3 после появления первого
подтверждённого листа: 24 предложения, из них **17 полностью проверенных словарём**;
49 с на страницу из 30 строк вместе с загрузкой модели, 0.3–0.7 с на строку после
прогрева (первый вызов 62 с).

**Наблюдаемые ошибки модели:** любит добавлять/переносить пунктуацию (предложения
«только пунктуация» принимаются лишь целиком); иногда переписывает слишком смело —
например `пазиі. организцни и. Судиславль` → `партийной организации.` с потерей
топонима (такое блокируется словарём); придумывает падежи (`Судиславль → Судиславле`,
`годе → года`). Удачные примеры: `ойца→отца`, `1д46→1946`, `Жизь→Жизнь`,
`пазиі→партийной`, `организоцни→организации`, `времся→время`, `зухнуло→утонуло`,
`натаи→найти`, `тогдо→тогда`.

**Журнал решений.** Каждое действие человека по предложению пишется в
`htr_suggestion_events`: `accepted_change` (одно слово), `accepted_line` (строка
целиком), `accepted_bulk` (массово проверенные), `dismissed` (скрыть), с текстом
предложения, фрагментом до/после и флагом «слово было в словаре». Запись
best-effort: сбой журналирования не ломает принятие правки. Потребителя у этих
данных пока нет — это заготовленный датасет для дообучения промпта и
confusion-профиля (см. § 8, п. 17).

### 6.6 Beam search с языковой моделью против greedy (хронологические фолды)

Обе колонки — один и тот же вызов распознавания, отличаются только декодеры; эталон —

LM для каждой страницы собран только из **подтверждённых страниц с меньшим id**, то есть
из тех, что были подтверждены раньше: ровно то, что есть у системы к моменту
распознавания (поздние листы ещё не написаны). Более слабый вариант —
`--leave-one-page-out`, скрывающий только саму страницу. Ширина луча 32, top-k 8,
α = 0.1, β = 0, бонус за слово 0.8.

| страница | текста автора в LM | greedy CER | beam CER | greedy WER | beam WER |
| --- | --- | --- | --- | --- | --- |
| 3 | 0 | 0.0949 | 0.0949 (фолбэк на greedy) | 0.3015 | 0.3015 |
| 9 | 1 157 | 0.0654 | **0.0628** | 0.2438 | **0.2388** |
| 14 | 2 356 | 0.0612 | **0.0532** | 0.1900 | **0.1700** |
| 16 | 3 512 | 0.0884 | **0.0758** | 0.2850 | **0.2539** |
| 17 | 4 648 | 0.0896 | **0.0686** | 0.3298 | **0.2461** |
| 18 | 5 772 | 0.0776 | **0.0639** | 0.3033 | **0.2701** |
| 19 | 6 975 | 0.0697 | **0.0514** | 0.2576 | **0.1869** |

| **всего (239 строк)** | | 0.0753 | **0.0632** | 0.2707 | **0.2297** |

Вывод: beam выигрывает на каждой странице, где в модели есть хотя бы ~1 000 символов
реального связного текста, и выигрыш растёт с корпусом: −2 % относительного WER на
странице 9, −35 % на странице 20 и **−15 % в сумме по восьми страницам** (WER
0.2707 → 0.2297) — итог занижают первые страницы, у которых модели почти нет.
При нуле связного текста LM знает буквы, но не знает, что бывает после пробела, и
немного **проигрывал** greedy (страница 3), поэтому ниже порога
`htr_lm_min_text_chars = 1000` распознаватель принудительно использует greedy. Счёт идёт
по `running_text_chars`, а не по общему размеру корпуса: модель, собранная только из
словоформ, имеет миллионы символов и всё равно не умеет расставлять пробелы.

**Проверка боевого пути.** В проде распознаватель берёт `author_<id>_char_lm.npz`
(9 258 символов подтверждённого текста автора) и получает словарь автора как мягкий
бонус за слово; на той же странице 20 боевой путь (`_build_decoder` с настоящим кодеком,
Bloom-словарём и словами автора) даёт CER 2.73 % / WER 11.46 % против greedy
5.64 % / 25.52 %. Эти числа сознательно **не** в таблице: это повторное распознавание уже
подтверждённой страницы, и её текст законно лежит в LM. Проверка доказывает только то,
что путь собран целиком и словарь доходит до декодера.

### 6.6.1 Настоящий корпус и второй проход (словесная KenLM): что дало

Первое и самое дешёвое улучшение — перестать учить символьную LM на одних словоформах.
Добавление **40 млн символов реального русского текста** (Leipzig Corpora, новости,
`rus_news_2020_1M`) при том же протоколе, тех же матрицах и тех же параметрах:

| | beam CER | beam WER | к greedy по WER |
| --- | --- | --- | --- |
| словоформы + 9 тыс. символов автора | 0.0632 | 0.2297 | −15 % |
| **+ 40 млн символов Leipzig** | **0.0582** | **0.2101** | **−22 %** |

Сильнее всего выигрывает **первая** страница (WER 0.3015 → 0.2764) — та самая, где
раньше модели не хватало и декодер откатывался на greedy; регрессий две и они малы
(стр. 9 и 20). Это подтверждает гипотезу: выигрыш ограничен не архитектурой, а данными.

Второй проход — словесная **KenLM**-модель (порядок 5, обучена на 102 млн символов
Leipzig), которая переранжирует 10 лучших гипотез beam. Вес подобран сеткой на
хронологических фолдах, выбор — leave-one-page-out (вес выбирается на остальных
страницах):

| | beam | + rescoring |
| --- | --- | --- |
| CER (вес выбран на других страницах) | 0.0582 | **0.0579** |
| WER (то же) | 0.2101 | **0.2082** (+0.9 %) |
| CER / WER (лучший вес на всех 8 страницах — оптимистично) | 0.0582 / 0.2101 | **0.0571 / 0.2032** (+3.3 %) |

То есть второй проход на этом корпусе даёт **мало**, и первый замер сказал обратное по
поучительной причине.

> **Ловушка: интерполированную модель KenLM нельзя «размешать» весами при запросе.**
> Первая сетка оценивала кандидатов уже интерполированным бинарником (general 0.5 +
> author 0.5) как «общей» моделью и сверху добавляла авторский ARPA. Поскольку текст
> автора был запечён внутрь этого бинарника, строки с оцениваемых страниц получали
> подозрительно хорошие оценки: WER как будто падал с 0.2101 до **0.1464**, оптимум веса
> убегал на край сетки, а guard выглядел вредным. На **чистых** компонентах (общая модель
> отдельно, авторский ARPA для каждой страницы собран без её текста) та же сетка даёт
> +1…3 %, а оптимум — вес около 0.5. Это та же утечка, что уже ломала одну таблицу
> символьной LM: страница не должна оцениваться моделью, которая её видела.

Правки, которые делает второй проход, — именно те, чего не видит символьная модель
(границы слов, окончания: `что б кататся → что б кататься`, `1879 годе → 1879 года`),
но на 239 строках это около одного слова из пятисот. Инфраструктура готова и
включается/выключается одной настройкой; честная рекомендация — перезамерить, когда у
автора накопится больше текста, либо заменить словесную модель на более сильную.

Две находки про KenLM на нашем корпусе: (`--discount_fallback`) на 235 строках автора
modified Kneser-Ney даёт отрицательный дисконт и `lmplz` отказывается собирать модель;
и `interpolate --just_tune` на таком объёме возвращает `nan` — веса приходится задавать
явно и подбирать по метрике декодирования, а не по правдоподобию.

### 6.6.2 Сколько даёт LM на сильной акустике (v12/v13) и повторный подбор весов

Всё в § 6.6 измерено на **базовой** сети, которая почерка не видела. В проде же работает
персональная дообученная модель, и там языковой модели чинить почти нечего. Чистое
сравнение — на двух страницах, которых дообученные модели не видели (23 и 24, загружены
после обучения v13); один и тот же char-LM фолд, одни и те же параметры beam, меняется
только акустика:

| акустика | CER к тексту v13 | WER к тексту v13 | **сколько символов изменила LM** | изменённых строк |
| --- | --- | --- | --- | --- |
| базовая | 0.0516 | 0.1842 | **2.51 %** | 37 из 58 |
| v12 | 0.0290 | 0.0974 | **0.82 %** | 18 |
| **v13** | **0.0249** | **0.0763** | **0.73 %** | 14 |

Первые две колонки — расхождение с тем, что сохранено в БД (правок пользователя на этих
страницах ещё нет), третья колонка эталона не требует: это расстояние между greedy и beam
одной и той же модели. С ростом акустики вмешательство LM падает в **3.4 раза** — ровно
ожидаемый эффект. Словесная LM (второй проход) на v13 меняет 0.05 % символов и на этих
двух страницах немного **ухудшает** WER (0.0763 → 0.0789).

Повторный подбор весов потребовал двух методических правок:

* **честные акустические фолды** — каждая страница распознаётся моделью, созданной *до* её
  подтверждения (v2/v7/v8/v9/v10/v11/v12 для стр. 3, 9, 14, 16, 17, 18, 19, 20, 22). Замер
  v12 на страницах, где она обучалась, измерял бы запоминание, а не распознавание;
* **строгий эталон** — `--only-corrected`: считаются только строки, которые пользователь
  реально исправлял. Иначе эталоном неисправленной строки становится вывод предыдущей
  модели, и LM штрафуется за расхождение с ним. Именно из-за этого старый α = 0.1 оказался
  занижен.

Сетка на 142 исправленных строках (CER / WER):

| группа акустики | α = 0.0 | α = 0.05 | α = 0.1 (было) | α = 0.2 | α = 0.4 |
| --- | --- | --- | --- | --- | --- |
| слабая (v2) | .1047/.3342 | .0964/.3045 | .0887/.2722 | **.0807/.2488** | .0799/.2550 |
| средняя (v7–v9) | .0549/.2167 | .0517/.2031 | .0493/.1920 | **.0460/.1760** | .0460/.1754 |
| сильная (v10–v12) | .0324/.1484 | .0312/.1415 | .0300/.1342 | **.0240/.1053** | .0240/.0987 |

α = 0.2 лучше **во всех** группах: вес не нужно уменьшать на острых логитах — скорее
наоборот. Итог по всему конвейеру на том же строгом эталоне:

| конфигурация | CER | WER |
| --- | --- | --- |
| α = 0.1 без второго прохода (что работало в проде) | 0.0653 | 0.2212 |
| **α = 0.2** без второго прохода | 0.0593 | 0.1998 |
| **α = 0.2 + второй проход** (w = 1.0, guard выключен, словесная модель только общая) | **0.0577** | **0.1957** |

Повторный подбор даёт **−11.5 % относительного WER**, из которых второй проход добавляет
последние 2 %; на почти всех страницах выбор падает на `guard=False` и `W_author=0`, то
есть и guard, и авторская половина интерполяции остаются не у дел.

**Оба протокола фолдов согласуются.** Тот же замер с буквальным
`--leave-one-page-out` (скрывается только сама страница) на тех же матрицах даёт
greedy CER 0.0753 / WER 0.2707 → beam CER 0.0622 / WER 0.2290 (+0.0131 CER, +0.0417 WER)
против +0.0121 / +0.0410 у хронологических фолдов. Различие ровно там, где и должно
быть: при leave-one-page-out в модели *первой* страницы лежат поздние страницы
(8 100 символов), поэтому она тоже улучшается (CER 0.0949 → 0.0851). Единственная
регрессия в обоих прогонах — страница 9 (WER 0.2438 → 0.2587). В таблице выше —
хронологические числа, потому что они описывают то, что у системы реально есть в момент
распознавания.

Две измеренные ловушки, каждая из которых превращала выигрыш в проигрыш:

* **словоформы без пробелов.** Синтетические «предложения» из 10 словоформ дали 28 млн
  символов фейковой межсловной статистики, которые утопили 0.3 млн символов реального
  текста автора: WER 0.37 против 0.27 у greedy. Связный текст — только настоящий;
* **утечка страницы в LM.** Артефакт, собранный со всеми страницами (в том числе с
  оцениваемой, с весом 30), показывал на странице 20 CER 5.64 % → 1.32 % и WER
  25.5 % → 5.7 % — это были её же слова. Числа в таблице выше утечки не содержат;
  воспроизводится через `scripts/measure_htr_decoders.py --chronological` (кэш
  матриц и фолдов переиспользуется ключом `--reuse-cache`).

### 6.7 Высота строки (96 против 128 px)

PP-OCRv6 предобучен на высоте 128, в конфиге проекта стояло 96 — это выглядело как
рассогласование масштаба. При этом экспортированный чекпойнт объявляет собственную
входную форму (`input=(1, 3, 96, 0)`), и kraken перезаписывает `config.height` значением
из чекпойнта, так что настройка до сети вообще не доходила. Замер на одном корпусе,
сплите и seed:

| прогон | запрошено | фактическая | val CER | val WER | base CER |
| --- | --- | --- | --- | --- | --- |
| A | из чекпойнта | 96 | 0.0303 | 0.1304 | — |
| A | 128 | 128 | 0.0325 | 0.1366 | — |
| B (`scripts/measure_htr_height.py`) | из чекпойнта | 96 | 0.0337 | **0.1366** | 0.0685 |
| B | 128 | 128 | 0.0337 | 0.1429 | 0.0685 |

Разброс между прогонами от стохастичности обучения (аугментация, порядок
редукций на CUDA) — около 0.003 CER, то есть того же порядка, что и сама разница.
Честный вывод: **128 нигде не лучше** (WER хуже в обоих прогонах, CER в одном равен,
в другом хуже), поэтому оставляем собственную высоту чекпойнта 96. Прогон B
воспроизводим, одинаковый base CER 0.0685 при обеих высотах подтверждает, что корпус
и сплит были одни и те же.

Механика: высота меняется только через явную опцию `htr_training_height_override`
(сама `htr_training_height` не работает — kraken перезаписывает `config.height`
значением из чекпойнта), а фактическая высота возвращается в
`training_metrics.line_height` (+`line_height_override_from` при принудительной) и
показывается в баннере обучения в UI.

## 8. Известные ограничения и открытые направления

**Метрики и валидация**
1. **Нет независимого holdout.** Все подтверждённые страницы входят в корпус, поэтому
   гейт сравнивает кандидата с базовой моделью на страницах самого автора
   (`holdout_used=false`). Вневыборочная кривая § 6.1 — единственная честная оценка.
   Резервирование целой страницы под оценку сделало бы гейт объективным.
2. Монитор чекпойнта использует accuracy kraken внутри обучения, а отчётный CER — наш
   тестовый путь с нормализацией (NFC/NFD): числа различаются (например 0.0314 против
   0.0325). Выбор «лучшей эпохи» оптимизирует не совсем ту метрику, что отчётная.
3. Валидация — 23 строки; это шумно (±1 строка ≈ 0.5 % CER).

**Распознавание**
4. Декодер — **prefix beam search** со символьной n-gram LM; он встроен в проект
   (`infrastructure/kraken/beam.py`), потому что `kenlm` не собирается на Python 3.13,
   а `pyctcdecode`/`torchaudio` недоступны. Kraken отдаёт матрицу вероятностей
   (`return_logits=True`), так что CTC-часть переиспользуется. Ограничение: словарь
   участвует только мягким бонусом за известное слово, а не жёстким ограничением
   (lexicon-constrained decoding не реализован).
5. Корпус **решается**: подключены 40 млн символов Leipzig (−22 % WER против greedy,
   § 6.6.1). Словесная KenLM-модель собрана (102 млн символов, `lmplz` + `interpolate` +
   `build_binary`), второй проход реализован и **выключен по умолчанию**: на сильной
   акустике он меняет 0.05 % символов и даёт +2 % WER по LOO, что в пределах шума, а стоит
   гигабайт памяти и задержку. Авторская половина интерполяции при 9 тыс. символов не даёт
   ничего измеримого (`interpolate --just_tune` на таком объёме не сходится — nan).
   Следующий шаг — не крутить веса, а дать словесной модели больше данных (или заменить её
   нейросетевой на N-best). Акустика: замеры § 6.6.2 сделаны на **дообученных** моделях
   (v2…v13) через честные фолды; на страницах без правок пользователя абсолютной точности
   получить нельзя — только расхождения и влияние LM.
6. Нет анализа макета страницы: колонки, порядок блоков, разделители не обрабатываются.
7. Склейка строк — эвристика (направление + шаг строк); при плотной волнистой строке
   возможны и лишние склейки, и пропущенные разрывы.
8. Геометрия слов у уже распознанных страниц не пересчитывается: правки в алгоритме
   действуют только на новые распознавания (пересчёт потребовал бы перераспознавания,
   а оно стирает правки пользователя).
9. bbox склеенных строк бывает вырожденным (наследие старого кода склейки) — на кропы
   обучения уже не влияет, но влияет на отображение и на фолбэк-кроп.

**Корпус и обучение**
10. 239 строк — очень мало. Аугментация — стандартная kraken, специальных искажений под
    тетрадный фон/наклон/росчерки нет.
11. Кропы — прямоугольные полосы вдоль базовой линии; перспективные искажения и
    выпрямление по дуге не применяются (модель ожидает именно полосы, поэтому это
    осознанный выбор).
12. Один автор = одна модель. Смешивание почерков не проверялось.

**Словарь**
13. Проверка не ловит осмысленные подмены (`карова`), опечатки с реальными словами и
    имена собственные, которых нет ни в словаре, ни в лексиконе автора.
14. Калибровка меряет только долю флагов на подтверждённом тексте; precision/recall
    флагов относительно реальных ошибок не измерялись.

**LLM-этап**
15. Термины базы знаний приходят с мусором из извлечения сущностей: в контекст попадают
    фрагменты вида `##ть`, `##дем`, `ака`, `до 2 час` — это шум в промпте.
16. Предложения «только пунктуация» нельзя принять по словам — только строку целиком.
17. Обратная связь **логируется, но не используется**: каждое принятое и отклонённое
    предложение пишется в `htr_suggestion_events` (`accepted_change` / `accepted_line` /
    `accepted_bulk` / `dismissed`, с текстом до и после и флагом «слово было в словаре»),
    но эти данные пока не влияют ни на промпт, ни на отбор примеров, ни на
    confusion-профиль. Это готовый датасет для следующего шага.
18. Контекст — только лексикон, confusion-профиль, примеры и ±2 строки. Смысловой
    контекст (тема страницы, имена из базы знаний в этой строке) не передаётся.
19. Всё синхронно в HTTP-запросе: обучение 3–4 минуты, правки 49 с на страницу; при
    росте корпуса потребуется воркер.
20. Альтернативы по словам (§ 4.1) содержат только варианты из beam-поиска: слова,
    которого акустика не предложила ни разу, в списке не будет. Для таких случаев
    нужен словарный поиск по отрезку слова (кандидаты в пределах 1–2 правок по
    словарю и лексикону автора, отсортированные по акустическому правдоподобию) —
    он не сделан.
